- 受保护知识文件不读取、不哈希、不改动、不暂存；真实配置、数据库、对象存储、API Key、代理和 Ubuntu 均未操作。没有真实模型、Embedding、图片或社媒请求。

## 3. 优先处理的正确性与安全风险

### A37 / P1：多页共享 Cookie 可导致工作区错投【协议复现＋源码】

`web/lib/contentflow-api.ts:97` 的请求使用实时共享 Cookie，但不携带页面预期工作区；`contentflow/routers/auth.py:787` 切区轮换共享会话。`web/app/contentflow-app.tsx:1241/1387` 加载与轮询没有身份/工作区代次约束，旧请求仍可能写回新页面。

本轮探针：先保存页面 A 的工作区上下文，另一个操作切到 B，再发送 A 页面准备的创建活动请求，返回 201，实际写入 B。它是同一用户已授权工作区间的误操作风险，不是陌生租户越权。真实双标签页交互尚未验收。

整改：写请求带预期工作区/会话上下文，服务端只用它核验一致性而不替代鉴权；不一致拒绝。跨页广播切换/退出；取消或隔离旧请求和身份缓存。关闭条件包括双页、快速切换、慢响应、后台轮询和失效会话。

### A05 / P1：生成入口没有用户操作级幂等【API 复现】

`contentflow/routers/runs.py:91` 每次先建新 run，再用新 run ID 生成队列键。同一个 `Idempotency-Key` 连续提交两次，本轮得到两次 202 和两个不同 run。发布入口的操作 ID 已实现，不代表生成入口也受保护。

影响：网络超时后重试、双击或重复提交可能产生两批内容和两批费用；本轮没有真实扣费。需要工作区内操作 ID、请求摘要、数据库唯一约束和原回执重放，同时区分明确“再生成一次”。

### A07 / P1：Worker 失去执行权后仍可能继续后续外部调用【源码确认】

`contentflow/worker.py:2141` 在整个 handler 返回后检查 `heartbeat.lost`；`provider_invocations.py:38` 的上下文只含 job/workspace，不含执行者与 attempt。工作流多个阶段、独立进度提交没有逐调用执行权门禁。

已有续租、最终所有权校验和未知结果恢复，不能说完全没有租约保护。但它们阻止最终提交，不能阻止旧进程继续执行下一个计费请求。需要调用前及领域写回的执行代次校验，并验证暂停→租约丢失→旧进程恢复；已送达供应商的请求仍须作为未知结果核对。

### A12 / P1：费用和资源限制没有形成完整约束【源码确认】

`contentflow/providers.py:438/473` 没有输出 token 上限，整体读取响应。账本记录、素材大小和存储配额不能替代工作区生成预算。活动部分数组缺少数量/元素长度上限，知识全文分块一次性发往 Embedding。

需要输入/响应大小、请求总时长、输出 token、每工作区排队和并发上限，以及预算预留、结算、未知费用保留和通知。私测先做硬上限，不必先建设完整收费系统。尤其不能仅凭“Agent 最多改写一轮”认为总成本已有上限。

### A41 / P1（发布验收）：健康检查可能将不可用版本标为 ready【新增隔离复现】

`contentflow/api.py:282` 只执行 `SELECT 1` 和存储检查，没有核对 Alembic head/必需 schema。生产启动又不自动迁移。

本轮将检查连接替换为**没有任何表的内存数据库**，`/health/ready` 仍返回 200、database=ok、storage=ok。没有删除现有表，没有连接真实数据库。

影响：漏迁移、错误数据库或不兼容升级可以在健康探针层被当成可接流量；不代表已发生真实部署故障。需要在启动或就绪门禁验证受支持迁移状态和关键 schema，检查失败不就绪。Worker 存活和完整业务验收另外检查，不把健康探针做成触发付费操作的检查。

### A08 / P2：正常的并发刷新可能撤销整个会话【协议复现】

`web/lib/contentflow-api.ts:34` 只在单页面合并刷新；`routers/auth.py:495` 遇到历史 refresh token 即撤销。本轮同一旧 Cookie 的两次刷新依次为 200、401，随后 session 也为 401。

需要保留重放防护的跨页协调/受限恢复协议；不能直接取消旧令牌检测。与 A37 一起验收真实双标签页、断线、后台恢复和未保存稿件保护。

### A09 / P2：配置快照和评测身份不完整【源码确认】

已冻结 Brief/风格，但 `workflow_service.py:78` 执行时重新取当前 Prompt 与 Provider。排队后修改配置，执行内容可能不是用户提交时的配置。

`prompt_eval.py:203` 的通过门禁匹配 provider 名、模型名、Prompt/suite hash 和输出契约版本，不绑定 API endpoint 或完整模型参数指纹。更换中转/端点但保留同名模型，代码上可能继续接受旧评测。这里没有伪造真实 Eval 或执行新模型请求。

需要冻结可复核且不含秘密的配置身份、索引身份及 Prompt 版本，并定义撤销策略；endpoint/参数变化需使对应评测失效。不能只靠模型字符串表示同一个服务。

### A39 / P2：AI 媒体缺少与人工上传一致的实际内容校验【新增隔离复现】

`media_providers.py:872` 检查响应形状/base64/MIME 字符串，`worker.py:863` 随后入库 ready，但没有实际图片解码规范化。

本轮把 12 字节 `not an image` 标为 image/png，经真实结果解析函数和存储函数后成为 ready。人工上传路径已有实际图片处理，不能说所有上传都没有检查；本轮未进行恶意媒体执行或 XSS 攻击实验。

需要所有来源共用安全解码、真实类型、尺寸/像素和文件大小限制；视频检查容器/编码/时长。ready 应表示可消费媒体，不仅表示收到若干字节。对象 checksum 能证明字节没变，不能证明它是有效图片。

### A40 / P2：确定性规则未覆盖最终发布的所有字段【新增隔离复现】

`review.py:16` 只检查标题/正文；`review_evidence.py` 调用时也仅传这两项。导出/脚本/部分平台还发送 hashtags 或独立 CTA。

本轮在安全正文外加入禁用词 hashtag，本地规则 passed=true，而 `export_markdown` 确实含该禁用词。不是权限绕过，AI 审核和人工确认仍存在，但“本地规则通过”的边界过窄。

需要按平台规范化最终发布文本后统一规则复核，清楚区分不可绕过规则和有审计的人工例外；不能只检查编辑器中最显眼的正文框。

### 平台成品能力仍未完整

- `publication_payload.py:9` 的公众号产物是安全转义的纯文本段落，还不是成熟图文排版/正文插图系统。结构化 layout 并不自动成为最终富媒体成品。
- 公众号指标接口尚未实现；抖音缺少 item_id 时不能可靠自动对账；小红书是导出/本机人工辅助边界。三个平台选项不能承诺三套完整自动运营。
- 风格 Skill 已存在，不需要重复发明安装入口；下一步是用户样稿/品牌事实/禁用表达如何稳定影响结果及如何评测。
- 应先做好公众号这一条真实主链路，随后按账号权限和实测证据逐平台扩展。

## 5. 交付、体验与企业差距

### 现阶段私测也应补齐

1. **发布版本的一致性**：代码、镜像、Web/API/Worker、数据库迁移、Prompt/模型必须作为一个候选版本签收。在制审核变更有新迁移 `b6c7d8e9f0a1`；本次 SQLite 通过不能代替 PG 升级/竞争与旧数据兼容测试。运行版本最后记录落后于源码，不能凭 GitHub 已推送就认为已上线。
2. **备份与恢复**：已有备份、校验、恢复资产，不是没有备份设计；仍需在当前测试部署上证实异机恢复、资料/向量/媒体一致性和可接受恢复时间。磁盘剩余空间大不等于灾备。
3. **告警实际到达**：已有指标与规则，但 `deploy/observability/README.md` 明确没有配置真实 receiver。需一次端到端故障→通知→处置→恢复演练；本轮未复查服务器实际运行配置。
4. **容量与稳定性**：2 核 4G 主机宜低并发 API Embedding；需要真实任务峰值、磁盘满、断电/重启、数据库不可用、网络超时和长期运行测试。此处不声明当前机器的实时内存/在线状态。
5. **未知结果可处置**：`routers/jobs.py:383` 的 retry/abandon 都写供应商已核对；无法表达“无法核实但停止继续”。应拆分已核实、接受重复风险、停止继续，不能为了操作方便伪填核对事实。

### 用户体验与可维护性

- `contentflow-app.tsx` 当前 **6,038 行**。初次 loadData 将最多 22 类请求放在 Promise.all；单项失败影响整批，且多集合最多加载 2,000 条再本地筛选。应按业务页加载、服务端筛选/分页、隔离错误，并支持真正的历史定位。
- 审核页已有未保存保护，但刷新、会话丢失、浏览器退出后的持久草稿恢复仍不足。项目/稿件/筛选未形成稳定 URL 深链接，不能方便分享、收藏和返回同一对象。
- 轮询按墙钟 updated_at＋两秒重叠推进；源码上不足以保证覆盖长事务晚提交或慢查询窗口。需要专项故障测试及可靠增量游标/重同步，不把两秒缓冲当事务提交序列。本轮未做 PG 晚提交竞争复现。
- 继续改进应是“下一步该做什么、为何被阻止、数据属于哪个项目、怎样安全恢复”，而不只是更多动效。键盘、读屏、窄屏和长列表仍需专门体验验收。
- 前端检查参考 [Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md)，本轮技能仅用于审查，不据此改版或声称所有无障碍项目通过。

### 扩大为不可信用户/企业服务后必须补齐

- **身份与秘密**：账号恢复、MFA/按需 SSO、会话管理、密钥生命周期和轮换演练。历史在聊天明文提供过的秘密应评估轮换；本轮未读取、测试或替换秘密，不重述其值。
- **纵深隔离与职责分离**：已有 RBAC/工作区过滤；还需运行/迁移数据库最小权限、跨租户负向矩阵，按风险选择 RLS。Prompt 双人审核不等于内容编辑/审核/发布已实现独立人员策略；个人内测不必强制双人，但企业策略要明确。
- **生命周期与审计**：文档更新/撤回、活动归档、租户删除、向量/对象/备份的保留和删除传播。审计哈希链有价值，但不能防同权限 DB 管理员重写整条链，需要按交付承诺设计独立归档/保留策略。
- **受控出网与反滥用**：已有官方 Origin/精确域名限制和部分跳转保护；还需统一外部客户端的解析地址、出口策略、资源上限和滥用控制。缺这些不等于本轮证明匿名 SSRF 成功。
- **真实运营体系**：支持的平台与账号权限矩阵、SLO、RPO/RTO、客户隔离、事故响应、升级/回滚、依赖与供应链持续检查、数据处理和授权边界。当前测试数或行覆盖率不能代替这些证据。
