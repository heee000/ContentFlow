## 3. 当前最应优先处理的风险

### A07 / P1：失去任务执行权后仍可继续外部调用

位置：`contentflow/worker.py:2149/2155`，`contentflow/provider_invocations.py:38`。

本轮实际 Worker + MockProvider：策划完成后将心跳标记为 lost，后续 **generate 和 review 仍执行**。最终 run 停留 running / reviewing，0 条已保存内容。已有心跳、过期转人工核对及结束时所有权检查，但没有逐调用/逐领域提交的执行代次保护。

风险：发生失联、租约失效或人工接管后，旧 Worker 仍可能发出额外付费请求或写进度。不是本轮发生真实扣费，也不是所有任务都会自动被新 Worker 重放。

验收条件：调用前和领域写回均检查 worker/attempt 代次；失权后不发下一次调用，迟到结果不能覆盖新状态。已经发送的远端调用仍可能完成，要保留未知结果和核对流程，不能承诺通用 exactly-once。

### A12 / P1：成本和负载没有完整硬上限

位置：`contentflow/providers.py:438/473`，`contentflow/schemas.py:241`，`contentflow/knowledge_service.py:80`。

源码确认：文本请求没有输出 token 硬上限，响应整体读取；部分 Brief 数组缺数量/单项长度上限；知识索引一次发送全部分块。认证限流、存储配额、有限改写次数已经存在，但不能替代工作区费用预留、生成并发/排队上限。

风险：有权限的用户反复创建新操作仍可占用供应商额度和 Worker；生成幂等只控制相同意图，不是预算。公开测试前尤其重要，不应直接称为匿名免费攻击入口。

验收条件：输入/输出/响应字节与批次限额、工作区并发/积压上限、预算预留与结算；未知结果继续占用额度，不能自动视为零成本后重试。

### A47 / P1：部分成功的稿件不能恢复

位置：`contentflow/workflow_service.py:193/208/211`，`contentflow/worker.py:1888`。

本轮公众号 Mock Agent 已产生 **107 字文案**，随后抖音 generate 注入 TimeoutError：run failed，**保存的 ContentItem 为 0**。再次核对 `result_json` 的实际键是 **`["ai_provenance"]`**，没有 plan/contents。调用诊断还在，不能笼统说所有结果和证据都丢失；但可供用户编辑的第一份稿件确实没有持久保存。

验收条件：按阶段/平台持久检查点，绑定配置和执行代次；明确部分成功，仅续作未完成部分。未知调用不自动重放。

### A49 / P1（恢复链路）：发布回执损坏或不可读时被当成没有请求

位置：`web/components/publication-preview.tsx:28`，`web/app/contentflow-app.tsx:3852`。

本轮实际 TS 模块的三项失败确认：损坏 JSON / `getItem()` 抛错返回 null；缺少 delivery_mode/publish_now 的四字符串记录也被接受。提交前无读回验证，删除不比对当前操作身份；还没有统一的发布意图只读恢复入口。新的 `publish_receipt_incomplete` 也应纳入“保留原编号”处理，不能笼统清理 4xx。

风险：恢复过程丢失原操作身份，用户可能重新创建意图。**同编号服务端幂等仍有效**；本轮未实际复现重复平台发布，不将推断写成事故。

验收条件：区分 absent/valid/invalid/unavailable；读不到时阻止新意图，提供只读核对；持久保存读回和身份匹配清除、组件重挂载/迟到响应保护；新增浏览器负向案例并纳入默认测试入口。

### A39/A40 / P1：素材 ready 和规则通过并不保证发布物合格

位置：`contentflow/media_providers.py:872` → `contentflow/worker.py:864/958`；`contentflow/review.py:35`、`contentflow/review_evidence.py:122`。

- **已复现**：12 字节 `not an image` 经真实生成解析/对象存储路径成为 ready / image/png。人工上传已有校验，生成/下载链路没有共用实际解码门禁。浏览器能拦部分坏图，不替代服务端所有入口。

验收条件：统一实际格式/解码/尺寸/像素与平台约束；校验最终标题、正文、标签、CTA、布局及渲染结果。SHA-256 证明字节相同，不证明字节是合法图片。

### A41 / P1：健康就绪可能是假绿

本轮临时空库 **0 表仍返回 ready HTTP 200 / database=ok**；Worker 入口仍调用 `create_schema()`。能执行 SELECT 1 不证明迁移、约束、pgvector 和必要表可用。

验收条件：独立迁移；API/Worker 验证支持的 schema 版本及必要结构，缺表/错版拒绝就绪；区分进程存活和业务可用，补升级失败与回退演练。当前候选迁移为 d8e9f0a1b2c3，真实数据库未迁移。

## 4. 新发现 A50：发布时间回执缺失时区（P2，阻断当前候选签收）

位置：`contentflow/routers/publishing.py:323` 的重新加载，`contentflow/schemas.py:538`，`web/app/contentflow-app.tsx:4314/6094`。

本轮完整后端不是全绿：立即发布用例在比较 API 返回的 scheduled_at 与 UTC 时间时抛出 `TypeError: can't compare offset-naive and offset-aware datetimes`。

独立临时 API 验证：首次确认与原样重放均 202、同一个任务，但都返回类似 `2026-09-23T20:01:47.007294` 的 **不带 Z/offset 时间**。新原子插入后重新从 SQLite 读取，驱动返回 naive datetime；API 无统一 UTC 序列化。前端 `new Date(value)` 在本机 Asia/Shanghai 将同一无时区字符串解释为比显式 UTC 早 **8 小时**。

范围：已确认 API 时间契约与本地日期解释问题，**没有证明 PostgreSQL 同样丢时区，也没有证明实际 Worker 发布会提前 8 小时**；数据库中的 UTC 排期与显示解释要分开。

验收条件：明确所有 API 时间为带时区 UTC，保持首次接受、重放、列表一致；覆盖 UTC/Asia-Shanghai/夏令时地区与 SQLite/PG。不要只在失败断言中强塞 tzinfo 掩盖对外契约，也不要撤销原子性修复来恢复表面绿色。

## 7. 公开测试和企业交付仍缺的系统能力

1. **扩大开放的安全边界**：以已有 RBAC/会话/审计为基础，完善角色/租户负向矩阵、数据库最小权限、业务反滥用与受控出网。媒体下载精确允许域名已存在，但不是连接目的 IP/私网隔离；扩大开放时按威胁模型验证 DNS/代理/出口边界，不把未演练风险称为已利用 SSRF。
2. **身份与秘密运维**：按实际用户需要补账号恢复、MFA/SSO、职责分离和密钥轮换/撤销验证；核查历史日志/凭据影响需单独授权。个人私测不必先堆大企业 IAM。
3. **数据生命周期**：知识撤回、租户导出/删除、保留期限、衍生内容与索引失效、备份中的删除传播；独立审计保留。已有存储账本/清理不等于这套治理。
