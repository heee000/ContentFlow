# 内容审核一致性与历史证据契约

更新：2026-09-24。对应 A04/A06/A38 与 A34 显式 null。它描述当前代码契约，不表示已部署；最终测试和源码签收见 `IMPLEMENTATION_PROGRESS.md`。

## 1. 审批的对象

- 编辑、通过、驳回都要求 `expected_version`，必须是严格正整数，不接受 bool、浮点或数字字符串。
- PostgreSQL 对内容行加锁，并在等待后重新读取 ORM 实例；版本变化返回 409。通过/驳回只能作用于 needs_review/blocked，同版本已经完成的人工作业不能再覆盖。
- 内容指纹覆盖 id、version、platform、title、body、hashtags、call_to_action、layout_json。模型证据必须同时匹配版本与指纹才是 current。
- 接口展示将证据区分为 current、stale、unversioned、missing，不修改原始数据库证据。旧稿没有版本绑定时不能自动升级为 current。
- 不改变字段的保存是 no-op：不升版、不取消批准、不重建素材，不制造新修订。

## 2. 编辑和人工决定

实际改稿先归档 superseded 原始审核，升版并取消批准，执行不收费的本地规则复查，再记录 edited、ContentRevision 和审计。原 AI 分数不再用于当前稿件。

审核 Brief 优先使用已经保存的 review.brief_snapshot，其次是生成 run 的 campaign_brief_snapshot，最后才对没有快照的历史稿读取关联活动。已有快照不因之后修改活动而静默漂移。

人工决定再次执行本地规则，记录人工版本、指纹、审核者、时间、理由与警告。以下情形的批准必须显式 `acknowledge_review_warnings=true` 且理由去掉首尾空白后至少 8 个字符：

- 当前本地规则未全通过；
- 没有当前版本 AI 证据；
- 当前 AI 审核未通过或标为 high 风险。

例外确认不把失败规则改写为通过，也不声称重新取得 AI 评审。保存/批准从不自动重新调用付费模型。素材未知结果门禁仍单独生效，确认内容警告不能绕过它。

替换 review_json 前记录 before_human_review，之后记录 human_approve/human_reject，避免旧稿第一次直接审核丢掉历史模型原文。这些记录、版本、审批、素材任务和审计处于同一事务；异常时全部回滚。

## 3. 页面协议

- 表单一旦编辑就固定原保存基线，轮询不能重挂载并清空脏稿。
- dirty、保存失败、版本冲突时禁用批准/驳回；保存成功立即采用响应中的版本。
- 保存/审批/重新载入互斥，进行中不允许切稿或离开；使用同步进行中标志防同一事件周期重复操作。
- 切稿、项目、工作区、页面和退出登录都检查离开保护；浏览器关闭/刷新有 beforeunload 提示。
- 保存成功但回执丢失时不盲重试；用户可保留输入，明确放弃本地副本并重新载入服务器版本，再决定是否审核。
- 当前 AI 评分不可用时显示不可用，不显示旧分或误显示零分。历史原文仍可查看。
- 历史查询有工作区/RBAC隔离、分页和迟到响应取消。viewer 可以看历史，但不能据此获得审批权。

这不是持久离线草稿功能：浏览器崩溃/会话失效后恢复仍属 A17。也不解决另一标签页共享 Cookie 切换工作区的 A37/A08。

## 3.1 A40 发布字段复查（2026-09-24）

`deterministic-v2-publication-fields` 的禁用词检查覆盖标题、正文、hashtags、独立 CTA，以及 layout/分镜中的递归字符串值和 JSON 键。保存和审批都运行该规则。长度、产品名、必含事实和 CTA 在正文中的要求仍按原规则检查，不把这些规则的语义偷偷改成“其他字段里出现即可”。

发布预览、排期和 Worker 共用 `load_release_inputs`，重新读取冻结 Brief 并运行新增字段检查。发现禁词时，旧 ruleset 的人工例外不再适用；只有当前规则、内容版本/指纹、审批人、具体规则结果均匹配且显式确认警告/足够理由的人工决定才可继续。该例外仍保存失败结果，不伪造通过。旧稿可修正具体字段、保存新版本并重新审核。

审批后新增的独立分镜 JSON 素材也必须检查所有字符串；其字节不属于内容审批对象，因此内容上的警告例外不能豁免素材禁词。上传、生成和最终对象读取都会拒绝，要求修正素材。图片/视频画面和音轨没有 OCR/ASR 或语义审核能力；详见 [媒体有效性契约](media_validity_contract.md)。本批不新增迁移，API/Worker 需同版升级。

## 4. 迁移和协调升级

- 审核迁移为 `b6c7d8e9f0a1`，前置 `a5b6c7d8e9f0`，新增 `content_review_evidence` 和工作区/内容/时间/id 分页索引。随后指标隔离迁移成为当前 head `c7d8e9f0a1b2`；备份 schema 校验为至少 34 张表，详见 [指标数值契约](metrics_validation_contract.md)。
- 迁移本身不改写旧内容、评分、人工决定，也不批量伪造新证据。首次实际改稿或人工决定时才归档原始记录。
- API/Web/Worker 应同版协调升级：旧 Web 缺少警告确认字段，旧 Worker 不产生版本绑定证据，混跑不能视为完成升级。
- 升级前备份数据库与对象，确认旧待审稿数量/版本和待执行任务。不要用本次合成测试作为真实稿件的批准依据。
- downgrade 会删除新审核证据表。测试只在可丢弃数据库上执行；真实回退不能直接删表丢历史，必须先安排证据备份、兼容版本和恢复演练。
- 普通 SHA-256 是内容一致性证据，不是对高权限数据库管理员的不可篡改保证；独立归档/保留策略仍属企业化工作。

## 5. 验收组成

- `tests/test_review_consistency.py`：绑定全部可编辑字段、旧证据归档、明确警告、no-op、严格版本/null、权限/租户隔离、冻结 Brief、历史分页和事务回滚。
- `tests/test_migrations.py`：前一 head 的真实旧稿升级保留、表/索引与隔离降级；既有迁移回归保留。
- `tests/test_postgres_integration.py`：改稿→审批、审批→改稿、批准→驳回、驳回→批准，含等待锁前持有旧 ORM 实例。不能用本机 skip 当通过。
- `web/tests/browser/review.spec.ts`：真实隔离 API/生产 standalone 的 dirty、失败、远端改稿、旧评分、导航、在途互斥、保存回执丢失、切工作区/退出、正常批准和非法 layout。
- 所有夹具都是合成资料，无 Worker 进行真实模型/素材/平台调用。测试结果及 CI 按确切源码版本记在进度页。
