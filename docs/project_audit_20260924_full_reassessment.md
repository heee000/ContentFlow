## 3. 必须优先解决的高影响问题

### P1 — A51：存储事务候选已有明显进展，但尚未形成可交付版本

修复前慢存储阻塞心跳的故障见 [上一轮报告](project_audit_20260924_execution_review.md)。**不要将该旧反例直接写成当前候选仍失败。** 当前候选已经：

- 用短事务先记录 `staging` 分配、精确 URI/checksum、来源 Job/领取令牌，并计入配额，再做外部对象写入；对象 I/O 不允许发生在持有执行权写锁的事务中。
- 失权或业务回滚保留可核对的暂存对象与账本，不冒充就绪、不自动删除、不提前返还配额。
- 增加管理员确认回收：来源任务终态/人工核对、冷却期、无业务引用、跨区隔离、精确删除与完成后返还配额；UI 有说明和确认。
- 当前正式回归通过，包含慢上传续租、失权保留、业务失败、配额与回收约束。

**仍缺**同版 PostgreSQL 行锁/并发、MinIO/S3 写入前后 kill、PUT 成功但响应丢失、管理员回收与恢复写入竞争、真实升级/恢复演练和回收 UI 浏览器回归。现有 staging 指标也需补积压年龄阈值和告警处置。验收这些之后才可关闭 A51；不应撤掉执行权门禁或简单延长租约绕过。

### P1 — A47：多平台生成失败会丢掉已经完成的可编辑成果

- 当前实际 Worker 先完成微信 `plan/generate/review`，第二平台 `generate` 注入 TimeoutError；最终 run `failed`，该 run 下内容 **0 条**。
- `result_json` 仍保留 `ai_provenance`，不能说调用证据全部丢失，但已完成的第一篇稿没有保存成用户可编辑成果。
- 证据：`contentflow/workflow_service.py` 的多平台循环先累积内存结果，全部结束后再保存内容（约 192–210 行）。
- 后果：重做浪费时间和可能已支付的费用；一个平台失败拖累全部平台。
- 关闭条件：按平台/阶段持久检查点，绑定 Brief/Prompt/模型/版本；保留部分成功，允许只补缺失部分。结果未知的供应商请求仍须核对，不能自动重放或承诺 exactly-once。

### P1 — A12：费用、输入输出和工作区资源尚无完整硬上限

- `providers.py:440–475` 文本请求没有输出 token 硬上限，响应整体 `read()` 后解析；`knowledge_service.py:78–84` 将全部分块一次交给 Embedding；Brief 多个数组缺少条目数/元素长度边界。
- 已有存储配额、认证限流和有限改写次数，但不能替代工作区调用预算、并发和排队上限。
- 后果：误操作、大文档、异常供应商响应或被滥用的合法账号，可能造成费用与内存/队列压力；本轮未实际消耗资金或实施压力攻击。
- 关闭条件：输入大小/分块批次、响应字节/token 上限、每区并发/队列长度、预算预留与结算、结果未知费用冻结、取消语义、人工处置；限制必须在调用前生效，而不只是事后显示账单。

### P1 — A39：AI 素材“就绪”不等于文件真的可用

- 实际 `asset.generate` Worker 接收合成 Provider 返回的 `image/png`、内容 `b"not an image"`：**12 字节仍保存，Job succeeded，Asset ready**。
- `worker.py:870–981` 生成结果存储分支没有等价的真实图片/视频解码验证。手工上传和搜索下载已有部分规范化，不能笼统说所有入口都无验证。
- 后果：损坏文件进入业务状态，后续预览、封面处理或平台提交失败；不是已证明这 12 字节可执行恶意代码。
- 关闭条件：所有来源共用素材接入规范：实际格式/尺寸/像素数/长度、解码边界、规范化、超限拒绝、必要的内容/来源核对，再允许 ready；失败有明确可恢复状态。

### P1 — A40：规则审核没有覆盖最终发布内容的所有字段

- 禁用词只放在 hashtags 中，title/body 无该词时，当前 `RuleReviewer.review()` 仍 passed；版本审核的规则证据构造也只含 title/body。
- 证据：`review.py:34–36`、`review_evidence.py:122`。本轮用“稳赚不赔”标签取得正反例，不涉及真实稿件或发布。
- 后果：审核“通过”与最终渲染的内容不是同一个审核对象。人工审核仍在，并非已证实绕过人工直接公开发布。
- 关闭条件：定义统一发布载荷，将标题、正文、CTA、标签、脚本等适用字段纳入规则与审核版本摘要；各渠道渲染一致，不让 UI 和 Worker 各审一部分。

### P1 — A41：健康检查可能绿色，数据库却不能承载业务

- 将 readiness 的数据库连接替换成空 SQLite 后，`GET /health/ready` 仍 **200 / database=ok**。`api.py:284–296` 主要检查 `SELECT 1`，没有验证 schema 兼容版本。
- `worker.py:2476` 启动调用 `create_schema()`；正式迁移、建表和运行身份的职责仍应分开。
- 后果：错误版本/缺表部署可能通过健康门槛后才在业务中报错。本轮不是证明真实 Ubuntu 当前缺表。
- 关闭条件：迁移独立执行，API/Worker 启动验证兼容 Alembic head/关键能力，拒绝不兼容组合；迁移身份与运行期 DB 权限分离，并测试旧/新 API、Worker、schema 协调升级和回滚。

## 4. 新确认并发缺陷与其他重要问题

### A52 / P2（新增）：编辑期间，旧生成素材会从 stale 复活为 ready

实际 Worker + 两个独立线程：旧 v1 素材生成中，另一线程通过真实 API PATCH 改正文为 v2；PATCH 200，旧素材先正确变成 stale。Provider 随后返回，Worker 继续使用先前读入的 Asset，最终写成 ready。

```text
edit_http_status=200
old_asset_after_edit=stale
final: job=succeeded, old_asset=ready, asset_version=1
       content_version=2, content_status=needs_review
       stored=true, bytes=8094
```

证据：`routers/contents.py:144/193`、`worker.py:1000/1077` 与 `_store_generation:964`；生成入口只在远程调用前检查 stale，返回后未按内容版本重新读取并锁定。轮询入口有相近结构，本轮没有单独故障注入轮询，不将其写为已复现。

**边界：现有发布版本/批准校验仍挡住该旧素材，本轮未发现因此实际误发旧封面。** 已确认的是业务状态复活、不必要对象占用和用户误解风险。应按统一 content→asset 顺序锁定并复核最新状态、版本和生成身份；在结果写回/激活前再次判断。已写出的过期对象保留可核对账本，不自动附着或再次收费；补生成、轮询、人工替换与改稿交错的 PG 回归。

## 5. 产品体验和可维护性：并非再加动画就能解决

本轮使用 web-design-guidelines 对照 [Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md) 审核界面代码；未做新的视觉改版或声称完成移动端/无障碍人工验收。

- **页面与请求耦合重。** `contentflow-app.tsx:1313` 首次同时加载约 22 组数据，大部分放在同一 `Promise.all`，单个非指标接口失败会影响整批初始化。应按当前页面和项目加载，独立错误/重试/取消，避免用户进入内容编辑却被无关运维接口拖住。
- **历史数据退路不完整。** API 客户端默认至多 20 页×100 条；提示使用筛选/历史视图，但页面部分筛选仍只过滤已加载数据。大项目中“不在前 2000 条”会被误以为不存在。应服务端筛选与游标分页，不以无限加载解决。
- **导航与恢复仍弱。** 主视图主要保存在组件 state，缺充分 URL 深链；sessionStorage 操作回执也不等于跨设备/关页恢复的业务草稿。已有未保存拦截与回执保护，不应重复说完全没有；下一步是可定位项目/稿件/任务的 URL、显式草稿状态和恢复入口。
- **实现过度集中。** 主要页面约 6000 行，Worker 约 2500 行；不是行数本身构成漏洞，而是跨流程复用同一状态和事务时容易漏掉第二入口。按领域服务/状态机/页面资源边界拆分，并保留契约回归，比纯粹移动文件更重要。
- **测试数量增长，业务不变量覆盖仍不够。** 43 条浏览器全部绿色仍漏 A52，859 项后端通过仍接受 12 字节假图片。要增加“任何入口都不能把过期变就绪”“任何 ready 文件可解码”“任何晚提交最终可见”等性质与交错测试；为每条风险规定关闭证据，而不是只追求总数。
- **审计记录需要唯一当前入口。** 旧汇总页叠加多个“最新”与不同 HEAD，容易把已修问题和当前问题混淆。本轮在旧入口标明历史区；后续应维护单一问题状态表（负责人、版本、验证、剩余门槛），保留原始证据但不反复复制结论。

## 6. 安全与运维的重大疏漏：这里是待验收风险，不是已确认利用链

1. **当前版本的运行证据缺口。** PG/MinIO、schema/API/Worker/Web 的同版组合、重启恢复、受控真实平台验收都未形成当前版本签收。旧版本 CI 通过不能覆盖 f0 暂存变更；也未检查 Ubuntu 现在跑哪版。
2. **秘密生命周期。** 已有加密与旧密钥解密退路不等于做过完整轮换。公开部署前应更换曾在聊天/非秘密库中出现的凭据，核查日志/备份/历史暴露，演练轮换、撤销和恢复；本轮未扫描或改动真实凭据，不声称已经泄漏给第三方。
3. **权限纵深。** 现有应用层 workspace 隔离不能代替运行期 DB 最小权限与迁移账号分离；RLS 可作为多租户纵深选项，但不能替代应用校验。需要独立验证横向/纵向越权、Cookie/CSRF、文件与渠道 URL 出站边界；域名白名单不等于网络层出站隔离，尚未证明存在可利用 SSRF。
4. **监控通知没有闭环。** 有 Prometheus/Grafana/规则，`deploy/observability/README.md:50` 明确未内置 Alertmanager receiver。需要真实接收人、严重级别、静默/升级、一次故障到通知到恢复的演练。单机看板并不等于有人知道凌晨失败。
5. **恢复要验证“机器和凭据都丢了”。** 已有备份/校验脚本和历史演练不代表当前 35 表/f0 候选可以恢复。需数据库、pgvector、对象、加密密钥及配置联合异机恢复，约定 RPO/RTO，验证可登录、可预览、可继续处理但不重复发布。备份成功只证明产生文件。
6. **用户与数据生命周期。** 公共服务需要账号恢复/撤权与会话管理，按实际对象增加 MFA/OIDC；资料导出/删除/保留、索引和衍生稿件传播、备份过期策略及审计访问权限。不是所有企业能力都要在个人私测前实现。
7. **容量与可用性承诺没有实测。** 2 核 4G 旧电脑可以继续低并发私测，但不能由一次成功推导可靠并发能力。需要队列积压/内存/磁盘/断网/睡眠重启测试和可达性/发布延迟目标。暂不要求微服务或多地域，先用单体单机证明有界运行和可恢复。
8. **真实平台边界不能扩大。** 微信已有历史真实测试不等于当前版本完成全链路签收；抖音/小红书授权、能力范围、上传/审核/发布状态仍须分别验收。浏览器脚本发布是可选受控适配器，不是绕开平台权限、验证码或账号规则的通用方案。

## 7. 距离不同交付阶段还差什么

| 阶段 | 当前判断 | 最低额外门槛 |
| --- | --- | --- |
| 开发者陪同的个人私测 | 可以继续，需保留人工审核和未知结果门禁 | 使用明确签收版本；一次一任务、保留备份与问题记录，不声称当前候选已部署 |
| 无需开发者值守的个人自用 | 尚不足 | 收尾存储/迁移、A52/A39/A40/A41、部分结果保留、基本预算、恢复/重启与清楚的错误处置；真实微信受控验收 |
| 个人公开部署 | 暂不放行 | 前项 + 域名/TLS/访问控制、密钥轮换、默认禁止 Mock、暴露面与出站限制、限制注册/容量、通知和备份演练；不是“有公网 URL”就完成 |
| 邀请制公开测试 | 暂不放行 | 前项 + 当前 PG 竞争测试、租户/角色负向测试、滥用和费用硬门槛、隐私/删除流程、问题受理与回滚；先限制用户与额度 |
| 企业完整商业项目 | 缺口显著 | 前项 + 可量化内容质量和 SLO、客户权限/SSO 按需、独立安全评估、合同/数据治理、运维值守、支持与审计流程、容量/灾备及版本兼容承诺 |

不提供“完成了 80%”之类无可复核比例。一个缺失的费用门禁或无法恢复的版本，就能阻断公开运营；页面/代码量不能抵消。当前还不需要为了“企业感”立即拆微服务、上 Kubernetes 或购买多套模型。

## 8. 建议实施顺序与验收标准

1. **冻结扩展、收尾当前候选。** A51/A41/A52，补正式失败回归、真实 PG/MinIO 交错/kill/迁移/回收测试，统一当前状态记录。关闭条件是同一版本完整证据，不是再一轮泛审或只补 SQLite 断言。
2. **避免丢成果和失控成本。** A47 检查点、A12 预算/背压、A46 模式策略、A09 执行快照；模拟第二平台失败、响应丢失、预算耗尽和失权，证明不会丢第一篇、盲重试或继续超额调用。
3. **保证成品和数据可信。** A39/A40/A28、A35/RAG、A33/A16/A34；所有媒体来源、最终发布字段、累计指标和晚提交都做统一契约测试。内容质量与可靠性可分别验收，不能把一个分数当成另一项完成。
4. **围绕用户任务做小规模体验重构。** 项目主页→内容→素材→审核→发布，按需加载、稳定标识/URL、历史查询和恢复，不新增分散入口；用真实用户独立完成一次操作并记录卡点。
5. **先邀请制，再考虑公网与企业能力。** 当前同版通过后，在重新确认真实调用范围和预算的前提下做微信/真实模型验收、限量长时运行、告警和异机恢复。再根据真实用户和风险补 OIDC/多租户运营等，而非提前采购复杂基础设施。

本轮只形成审计和计划，不把以上建议记为已经修复。已有在制代码完整保留，公网部署计划继续冻结；后续实施需从该候选断点衔接，不重新推倒已实现的幂等、执行权与回执保护。
