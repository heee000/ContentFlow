# 最终发布物绑定 v1

2026-09-23，A25/A26 的发布物、最终预览和确认回执边界。清单不是对抗数据库管理员篡改的数字签名；预览使用应用密钥签名，不代表用户已经完成真实平台验收。

## 解决的问题

旧发布任务只记录正文版本。Editor 排期后换选封面，不会增加正文版本，Worker 会读到新封面并发布。现在创建任务时把当前正文、选用素材和渠道配置绑定到 `request_json.release_manifest`；执行、安全重试与脚本回退必须匹配这份记录。

记录包含契约版本、内容 ID/版本及正文摘要、渠道 ID/配置摘要、确定性排序的素材 ID/URI/SHA-256/大小/类型/来源及元数据摘要。渠道凭据密文仅参与摘要计算，不复制密文或明文到记录、响应或日志。连接测试的状态变化不改变发布物；账号凭据轮换或配置改变则需要新确认。

## 行为与边界

- 所有选用素材必须 ready、有工作区内的存储 URI、大小和 SHA-256 才能排期。未准备完毕应返回素材步骤，不再先排入必然失败的任务。
- 创建记录、执行前核对时按内容→渠道→素材的顺序持锁；已有任务先锁自身 PublishJob，不倒过来锁素材→内容。等待锁后重读，防止使用 ORM 旧缓存。
- 官方分发在同一事务中完成检查并登记开始，提交后才调用平台。传给适配器的是脱离 Session 的内容/素材/渠道副本，后续编辑或 ORM 过期不会把新的字段偷换进去。已经开始的分发以该次固定副本为准，不声称改稿能撤回已发出的请求。
- 素材在适配器实际读取时核对大小和 SHA-256，不接受记录之外的 URI。检查使用的就是最终发送/导出的字节，不做“先校验一次、之后不受控重读”。官方 API、导出和脚本包共用此层。
- 任务创建后换图/改稿/修改发布配置：待执行的旧任务会拒绝，需重新确认并创建新任务。安全重试与脚本回退不能借机重新拍摄一份不同发布物。切换为脚本本身沿用已有审核者授权及审计，不改已绑定的正文/素材/渠道摘要。
- 没有 manifest 的旧待执行任务不自动补造确认；已提交、已完成、草稿已创建等领域终态仍优先返回，避免因为升级再次调用平台。既有结果不确定/人工对账语义保留。
- SHA-256 校验失败只阻止错误文件发送，不保证所有适配器都能证明“未产生副作用”。微信封面读取在平台写入前，因此沿用 read_assets 安全失败；其他不确定情况仍保守核对，不盲目重试。
- 脚本包生成沿用既有事务与存储补偿；本次不宣称消除了所有存储 I/O 持锁时间或实现了外部对象版本保留。

## 验收与尚未完成

隔离测试覆盖排期后更换不同文件的封面、正文/配置/校验和漂移、安全重试与脚本回退、旧任务拒绝/终态重放、提交后并发修改及 Session 过期、素材真实字节校验。微信 MockTransport 仅允许 token GET，校验失败没有任何平台 POST。另有 PostgreSQL 排期/选图竞争测试；实际结果以实施进度页及确切提交 CI 为准，不将本地跳过计为通过。

本轮已增加以下确认协议和正式验收；具体运行结果以 [实施进度](IMPLEMENTATION_PROGRESS.md) 为准。浏览器与 PostgreSQL 的证据不能互相替代，也不因此声称已解决 A04 未保存审批或 A06 审核版本。

## 最终预览与操作回执

- `/publishing/preview` 和确认接口都必须携带同一 `request_id`。正文/素材/渠道清单、执行方式、时间与操作编号一起形成指纹；15 分钟凭证绑定工作区、当前审核者和该指纹。签名不包含凭据明文。版本字段必须为整数 1，不能使用 bool 或浮点值。
- 最终页面使用与连接器共用的纯渲染函数，展示实际正文、主封面/视频、目标账号、草稿或公开提交行为及精确字段；不是平台最终排版截图。实际使用的素材加载成功且审核者勾选后才可确认。
- 预览素材接口按工作区与 reviewer 权限隔离，读取同一 SHA-256 的实际字节；同大小篡改、超长和缺失均失败。**确认事务本身不重复读取全部对象**：若文件在预览成功后被外部改坏，排队仍可能成功，但适配器使用时的逐字节校验会阻止错误文件发送。没有宣称数据库与对象存储之间存在原子事务。
- 同一工作区的操作编号对应一个请求摘要和一份任务回执。相同编号/相同原始确认返回原任务，即使凭证过期、正文改稿、渠道失效或任务取消，也不增加任务或分发 Job；换编号不能复用原签名，换请求不能借用原编号。数据库唯一约束与 SAVEPOINT 处理竞争，只由胜者排队和写一次确认审计。
- 等待内容锁之后再次查回执，避免另一个请求已经创建任务并改稿后，等待者因旧正文/过期凭证校验而丢失原回执。PostgreSQL 并发验收覆盖相同请求、同编号不同模式、同编号不同内容，以及胜者提交时已改稿。
- 浏览器发出确认前先持久化完整原请求；存储失败则不发送。网络/5xx/408/429 或编号冲突保留原请求、锁住新操作，刷新后明确重试原请求；不偷偷刷新预览、更换操作编号或自动换渠道。凭证属于同一账号/工作区，切换身份不能使用上一身份的待核对操作。
- 丢失回执后的成功重放只意味着找到了原任务，不意味着平台已发布。用户主动清理恢复记录也不取消服务端任务；必须先核对列表。浏览器存储并非跨设备永久账本，用户有意新建并重新确认仍属于新操作，不承诺全局内容只发布一次。

## 兼容性

这是尚未部署的在制协议收尾：旧客户端缺少编号/预览凭证会被拒绝，旧在制凭证未绑定编号也不能创建新任务；缺少新请求摘要的旧回执返回冲突，必须核对而不是自动替换。升级时同步更新 API、前端、Worker 及调用脚本。现有终态、未知结果与历史数据库证据不被重写。

浏览器回归入口和隔离要求见 [浏览器验收](browser_acceptance.md)。真实用户体验、目标主机部署和真实平台投放仍须独立签收。

## 将来部署的前置检查

本轮没有部署。将来部署必须先阻止新的发布请求、确认没有正在执行/结果不确定的分发，再协调升级 API 与 Worker 为同一提交；不能让旧 Worker 继续消费新 API 创建的任务，因为旧 Worker 不认识此清单。先核对两者版本与队列，再恢复受控操作。不得用清空队列、修改终态或补造清单来消除旧任务；旧待执行任务需用户重新确认，已提交的任务继续走原有对账。此步骤仍要与输出契约 v1 的受控 Eval、备份及回滚安排一起签收。
