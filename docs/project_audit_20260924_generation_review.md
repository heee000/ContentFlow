## 3. 新发现

### A48 / P1：发布接受并非完整原子事务（已在 SQLite 复现）

位置：`contentflow/routers/publishing.py:295`，`contentflow/db.py:33`。

复现步骤：使用临时 SQLite 和合成已审核内容取得有效预览；在确认入口向 `record_audit` 注入异常；查询发布记录、分发 Job 和审计，再原样重放同一确认请求。

实际结果：

1. 首次确认 **HTTP 500**。
2. 数据库已留下 **PublishJob.status=queued**，对应 **dispatch Job=0**。
3. 同一操作编号/请求重放 **HTTP 202**，返回同一孤立发布记录。
4. 重放后仍 **dispatch Job=0、接受审计=0**。用户看到已排队，实际不会被队列执行。

原因：SQLite 当前连接事务模式下，读取没有先建立实际外层写事务；首次写发生在 SAVEPOINT，释放后 PublishJob 已持久化，随后队列/审计的回滚不能撤销它。现有 A05 路径已专门处理这一边界，但旧发布路径未同步处理。

范围限制：**本轮没有证明 PostgreSQL 有同样的 SAVEPOINT 行为**；正式配置要求 PG，不能把此结果写成当前 Ubuntu 已发生的事故。SQLite 仍是受支持本地测试和大量验收的路径，行为必须一致。它与 A44 通用队列的整 Session 回滚是不同根因。

关闭条件：确保发布记录、分发 Job、确认审计在同一实际事务中提交；异常应全无残留或全部成功。补 SQLite 与 PG 的审计/入队/提交失败回归，并明确已有孤立记录的只读检测与人工修复方案；不能简单给旧回执补队列而忽略是否已有外部副作用。

### A49 / P2：发布回执存储失败时的恢复边界弱于生成回执

位置：`web/components/publication-preview.tsx:28`，`web/app/contentflow-app.tsx:3852`。

- 在实际 TS 模块转译执行中，损坏 JSON 和 `getItem()` 抛错都返回 **null**，与“确实没有待核对请求”无法区分。
- 仅有四个字符串字段、缺少 delivery_mode/publish_now 的不完整记录也会被返回为合法意图。
- 源码确认提交前 `setItem()` 没有读回校验，清除也未比对当前记录身份。新生成回执已有更严格处理，发布尚未统一。

影响：原请求可能已经接受，恢复状态却被误当作空，新确认可以覆盖原记录。**服务端同编号幂等仍有效**；本轮未做“损坏记录→换编号→重复平台发布”的浏览器/真实平台复现，不将风险推断写成已发生重复发布。

关闭条件：区分 absent / valid / invalid / unavailable；损坏或不可读时保留证据并阻止新意图，提供只读核对；保存须读回确认、清除须身份匹配。补实际浏览器损坏/拒读/静默写失败/离页迟到回执测试，而非只覆盖 setItem 抛错。

## 4. 亟需整改的高影响问题

### A07/A12：失去执行权仍能继续调用，费用也没有硬预算

位置：`contentflow/worker.py:2149/2155`，`provider_invocations.py:38`，`providers.py:438/473`。

本轮用真实 Worker 和 MockProvider：策划返回后令 heartbeat.lost=true，随后 **generate 和 review 两次调用仍执行**；到 handler 结束才拒绝队列完成，run 保留 running/审核中进度。没有真实供应商或费用调用。已有心跳和完成时校验，缺的是**每次外部调用前与领域写回时**的执行代次门禁；部分 handler 自行 commit，末尾回滚不是通用补救。

同时没有完整工作区费用预留/结算、生成并发/积压硬上限，文本请求无输出 token 硬上限且整块读取响应。A05 只防同一个业务意图重复接受，换新编号仍可接受新任务，不能当作预算。

先做执行代次与失租停止、输入/输出/响应字节和队列上限，再做按工作区预算、未知结果占用额度和人工核对。已发出去的调用可能继续完成，不能承诺远端通用 exactly-once，也不能把 unknown 自动记为零成本后重试。

### A47：多平台生成缺持久检查点

位置：`contentflow/workflow_service.py:192/207/210`。

本轮第一平台实际 Mock Agent 完成 **107 字文案**，第二平台注入 TimeoutError 后：**run failed、保存内容 0、result_json 空**。已经有调用账本/摘要，不是所有证据都不存在，但用户可继续编辑的成果没有保留。

按平台/阶段保存与执行配置绑定的检查点，显示部分成功，只续作未完成部分；未知供应商结果进入核对，不整批盲重跑。

### A39/A40：素材与最终发布字段没有统一有效性门禁

- `media_providers.py:872` → `worker.py:864/958`：本轮再次把 **12 字节 `not an image`** 经实际解析/存储路径保存为 **ready / image/png**。人工上传已有解码校验，生成/下载入口尚未共用。浏览器预览部分能阻止坏图确认，不替代服务端校验和其他调用入口。
- `review.py:35` / `review_evidence.py:122`：禁用词只放在 hashtags 时仍 **passed=true**。抖音/导出/脚本渲染会使用标签，公众号并不发送同一组字段，必须按实际发布物校验，不能笼统说每个平台都会泄漏标签。

统一实际解码、格式/尺寸/像素及平台约束；规则覆盖最终文本、标签、CTA、布局字段及渲染结果。对象 SHA-256 只能证明同一批字节，不能证明这些字节是有效图片。

### A41：就绪检查与迁移不形成交付门禁

`api.py:284` 对 **0 张表**的临时数据库仍返回 **200 / database=ok**；`worker.py:2445` 仍执行 `create_schema()`。连通性不等于必要表、约束、pgvector 和 schema 版本正确。

API/Worker 就绪应验证支持的迁移版本及必要结构，生产 schema 变更归独立迁移步骤。当前候选 head=`d8e9f0a1b2c3` / 至少 35 表；本轮没有迁移真实库。

### A44：通用入队冲突可能撤销调用者的业务修改

`job_queue.py:59` 唯一键冲突直接回滚整个 Session。本轮受控“查重 miss + 实际 SQLite 唯一冲突”后，函数返回原 Job，却撤销了此前 flush 的 Workspace 名称修改。

已验证机制，尚未签收真实 PG 业务并发入口；需明确局部事务或整笔失败，补两会话和领域调用链回归。不能用“返回了已有任务”掩盖前序业务已回滚。
