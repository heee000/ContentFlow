## 3. 新增：应优先修复的安全与正确性缺陷

### A30 / P1：平台 token 可通过发布错误暴露给 viewer【隔离端到端复现】

- 证据链：`contentflow/connectors.py:364` 上传请求把 access_token 放在 URL 查询参数；`:370` 的 `raise_for_status()` 产生包含请求 URL 的 HTTPStatusError；`contentflow/worker.py:1517` 把 `str(error)` 拼入 `PublishJob.error`；`contentflow/routers/publishing.py:79` 对普通当前成员开放列表，`schemas.py:494` 返回 error。
- 复现：真实的隔离 API 创建预览和发布任务 → Worker 使用 MockTransport，鉴权返回虚构 token、素材上传返回 500 → 临时成员降为 viewer → GET 发布列表仍能读出虚构 token。没有使用真实凭据。
- 影响：平台凭据虽加密保存，异常路径仍能越过角色边界。Worker 的 `logger.exception` 还可能输出带请求 URL 的异常链，不能只修页面序列化。
- 修复方向：连接器边界产生受控错误码、阶段、状态码、脱敏关联号；数据库/API/日志禁止存原始异常正文和带凭据 URL。统一覆盖微信、抖音、连接测试、分发和对账，而非单一 catch。
- 关闭标准：模拟鉴权/上传/建草稿/提交/查询的 HTTP、网络、JSON、平台错误，断言 API、数据库和捕获日志均无秘密哨兵；viewer 只能看到安全摘要。修复后另行授权检查历史错误/日志，确认受影响凭据后轮换，不在审计中擅自删除证据或更换密钥。

### A31 / P1：租户可配置连接器请求地址，形成 SSRF 攻击面【代码确认＋离线请求目标复现】

- `schemas.py:422` 的 ChannelCreate.config 为自由字典；`routers/channels.py:24` 主要验证凭据有值，不验证 api_base。`connectors.py:174/294` 直接采用该值，`worker.py:547` 的连接测试会使用它。
- 探针表明 `http://127.0.0.1:18789` 通过校验，并成为模拟请求目标。没有连接真实内网，未证明任何实际内网信息已泄露。
- 前提与影响：需要工作区 admin 权限并触发连接测试/发布，不是匿名 SSRF。工作区管理员不应自动获得 Worker 所在网络的访问权；将来允许不可信租户时风险更高。已有模型/媒体 HTTPS 与下载白名单没有覆盖这条渠道路径。
- 修复方向：正式社媒连接器固定官方 HTTPS Origin，测试通过依赖注入替换 Client；如确需自建代理，由部署管理员设置独立许可名单，限制解析地址、重定向与出口，不交给任意租户 JSON。
- 关闭标准：创建入口和运行入口都拒绝 HTTP、用户信息、query/fragment、内网/回环/link-local 目标；历史已存配置也不能绕过。出口防护仍须独立验收。

### A32 / P1：字符串 false 会变成“公开发布”【模拟连接器复现】

- 同一自由 config 接受 `{"auto_publish":"false"}`。`connectors.py:391` 按 Python 真值判断，非空字符串是真；而 `web/app/contentflow-app.tsx:3945` 用 `!== true` 判断，会显示“只创建草稿”。
- 复现：输入上述字符串时模拟连接器实际进入 `/freepublish/submit` 并返回 submitted。未向微信发送请求。
- 在制最终预览会显示服务端算出的公开发布行为，提供了一层提醒，但同页安全提示仍矛盾，且错误配置不能靠用户发现来兜底。
- 修复方向：为各平台建立封闭类型化配置；该开关只能接受严格 bool，拒绝字符串、整数、数组、对象及未知危险字段。后端执行分支同样严格比较；旧数据审计后阻断异常值，不可直接 `bool()` 批量转换。
- 关闭标准：false/true 与 `"false"`/`"true"`/0/1/null/数组等矩阵，页面、预览和连接器语义一致；只有明确 true 才进入公开提交。

### A33 / P2：指标快照被直接相加，重复观察变成更多“效果”和“样本”【隔离 API 复现】

- `routers/metrics.py:65` count 快照、`:66` 起 sum 全部快照；`worker.py:1788` 每次拉取新增快照；`connectors.py:270` 直接保存平台 play_count 等数值，没有计算增量。
- 同一发布任务两次记录累计曝光 100→150，汇总得到 250；同一篇作品计为两个样本。当前接口也不区分累计量和时间窗增量，因此无法保证经营复盘口径正确。失败/未完成的发布也可人工录入指标，样本解释需补齐。
- 修复方向：定义指标类型、统计区间、来源和去重键；累计量按作品取目标时点最新有效快照，增量按不重叠区间聚合；样本数统计 distinct 作品，处理补报、更正和计数下降。阈值建议在口径修正前不能当作可靠结论。
- 关闭标准：单作品多快照、多作品、乱序补报、重复输入、历史更正、累计下降、平台/活动过滤均有明确预期。

### A34 / P2：PATCH 接受显式 null，但数据库拒绝并返回 500【隔离 API 复现】

- `schemas.py:348` 把 title/body 等字段声明为可空；`routers/contents.py:155` 对显式提交值直接 setattr；ContentItem 正文非空。探针 `body=null` 返回 500，数据库回滚保留旧 v1。
- 影响不是已证实的数据丢失，而是 API 契约与数据库不一致：客户端错误变成服务器故障，且错误 SQL 日志还可能携带正文参数。
- 修复方向：区分未提交与提交 null，非空字段在 API 校验返回 422；对 title/body/标签/排版做一致结构限制。相同模式应检查 CampaignUpdate 等其他 PATCH。
- 关闭标准：缺省不修改；非法 null/空白/类型/超长在落库前拒绝；有效更新仍保持版本冲突和原子回滚。

### A35 / P2：Embedding 响应未校验 index 唯一性和范围，可能静默错配知识向量【离线适配器复现】

- `contentflow/embeddings.py:240` 只按响应 index 排序，再检查数量、维度和有限数值；没有要求 index 为严格整数、唯一且完整覆盖输入的 `0..n-1`。`knowledge_service.py:89` 随后按位置 zip 文本和向量入库。
- MockTransport 对两个不同输入返回两条 1024 维向量：index 为 `[0,0]`（重复）及 `[-1,2]`（越界）均未报错；合法乱序 `[1,0]` 也被接受。没有真实 Embedding 调用，也没有写入真实索引。
- 影响：兼容接口出现错误响应时，数量和维度正确仍可能把不对应的向量绑定到文本，表现为检索质量下降而非明确失败。不能据此声称现有供应商曾返回此类数据，或真实知识库已损坏。
- 修复方向：先严格校验整份响应及完整 index 集合，再按输入位置重建向量；坏响应不得落库。与 A11 的模型/索引身份、有限批次和原子重建一起关闭。
- 关闭标准：正确顺序/乱序、重复/缺失/越界 index、bool/字符串/小数 index、数量/维度/有限性矩阵；异常结果不替换旧可用索引。此次只是审计，没有实施修复。

| A22/A23 · 交付门禁 运维与真实平台 | 有备份、监控、部署和故障测试资产；observability README 明确没有真实 receiver；本轮没有当前异机恢复/告警到达/主机峰值或完整渠道证据 | 异机恢复、通知/恢复消息、断电与磁盘满、2 核 4G 峰值与长稳、真实账号成功/异常矩阵；Tailscale 不等于固定微信出口或主机高可用 |
| A24 · P2 状态与文档漂移 | 历史交接 2283 行含多个旧配置和验收层次；此前进度还写预览“待做”，实际工作树已经有在制实现 | 当前状态入口区分已提交、未提交、已测、已部署、外部签收；历史记录归档保留，不复用旧绿色冒称新版本 |

补充代码观察：`worker.py:860` 的 AI 素材落库路径没有复用人工图片的解码/像素/单帧规范化，主要信任 Provider 声明 MIME 与受限字节；视频也缺真实容器/编码探测。建议统一素材内容校验和隔离处理。这是实现差距，未在本轮制造恶意媒体或宣称已实现攻击。

平台支持也应明确分层，不能用三个平台选项代表三套完整自动运营：微信的指标拉取目前明确抛出 NotImplementedError；抖音适配器没有可靠的自动发布对账且缺当前真实账号验收；小红书是人工导出/本机辅助流程，非官方全自动发布。保留人工最终点击本身是有意的安全边界，不是需要偷偷绕过的缺陷。公众号现有发送正文以转义纯文本段落为主，完整图文排版、正文插图和平台效果预览仍是可继续建设的产品能力。

## 5. 本轮不应重复报成“没有”的能力

- 内部 PublishJob 与 Job 同事务，已有命令 Outbox 语义；缺的是外部事件 Inbox、平台原生幂等和跨平台最终收敛，不能再泛称“没有 Outbox”。
- 已有租约续期、最终所有权检查、未知结果人工核对、Provider 调用账本、存储配额与核对；缺的是逐调用 fencing、费用硬预算和完整运行闭环。
- 已有真实 PostgreSQL/MinIO 的历史 CI、进程/数据库故障用例、Prometheus/看板、源码/SBOM 来源证明。缺的是当前工作树验收、真实通知、目标环境恢复，以及部署端证明/回滚闭环。
- A03 严格 bool/有限评分及版本契约已经实现。A32 是渠道配置的另一条类型边界，不能用模型输出修复证明它也安全。
- A25 清单已经防止排期后换图静默改变实际发送字节；本轮在制前端还需 token、权限、改图、过期、回执丢失、刷新和并发 E2E。不得倒退称清单完全不存在。

## 6. 推荐实施顺序和验收终点

1. **先阻断泄密和误发**：A30/A31/A32；增加失败的正式回归后实现修复。补各连接器统一类型/错误/目标策略，不只在单页面加提示。
2. **收尾当前用户旅程**：A25/A26 在制改动；同时 A04/A06，保证改稿、保存、审批、最终图文确认、回执重放的对象一致。当前 API 新增必填 token/操作 ID，升级必须协调 API/Worker/Web，不能直接把半成品混版部署。
3. **让外部调用和费用可控**：A05/A07/A09/A12/A14，先为小规模私测设置明确上限；不为当前单人场景先建设复杂微服务网关。
4. **把内容与复盘做成真实产品**：A28、A10/A11/A13/A35、A33；跨行业事实与风格金标、人工质量验收、可解释引用、Embedding 输入输出对应、正确指标口径。
5. **真实运行签收**：E2E、主机容量、异机恢复和告警到人；再按开放范围推进身份、租户、数据、密钥、出网、制品与回滚治理。公网计划不因审计自动恢复。
