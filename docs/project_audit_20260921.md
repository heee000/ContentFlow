## 1. 结论和证据边界

当前项目已经有真实的产品骨架：PostgreSQL、持久任务队列、独立 Worker、工作区/RBAC、安全 Cookie、内容版本与人工审批、调用账本、发布对账、Prompt 治理、对象存储账本、CI 和运维资产。不能再把这些记成“尚未实现”。

但“主链路曾经跑通”与“跨入口规则一致、异常可恢复、可以交给普通用户长期使用”仍有明显距离。本次重新发现多处实际逻辑缺陷，尤其集中在素材重试、用户选择、审核版本及模型输出的信任边界。当前适合受控私人测试，不建议据此开放多用户公网测试或承诺商业可用性。

## 2. 应优先修复的具体缺陷

### A01 · P1 · 素材重试绕过未知结果的人工核对门禁【复现】

- 证据：`contentflow/routers/assets.py:531`；`contentflow/routers/jobs.py` 的通用重试保护；`contentflow/worker.py:1910`；`contentflow/provider_invocations.py:90` 起的请求键构造。
- 触发条件：真实素材请求结果不确定，旧 Job 已是 `manual_review`，关联 Asset 被标为 `failed`；拥有 editor 权限的人调用素材重试入口。
- 结果：通用 `/jobs/{id}/retry` 返回 409，但 `/assets/{id}/retry` 返回 202，创建一个新的 queued Job；旧人工核对任务仍未解决。新 Job ID 改变本地 ProviderInvocation 账本请求身份。
- 2026-09-23 证据修正：HTTP 媒体适配器实际发给供应商的生成键来自 `worker.media_generation_idempotency_key(asset)`，同素材/版本保持稳定，不等于上面的账本请求键。因此新 Job 不意味着必然重复计费；是否能去重还依赖目标服务遵守媒体契约。本轮原始复现是人工构造 manual_review 状态；当前 asset.generate 自动恢复政策原本是 provider_idempotent，并非所有素材异常都会自动进入 manual_review。人工门禁绕过仍成立，但不能据此声称实际供应商已经重复收费。
- 影响：可能重复调用/计费、产生迟到素材和混乱状态。这是已登录的工作流安全门禁绕过，不是匿名越权或已发生重复扣费的证明。
- 同类审查点：`change_asset_source`（`assets.py:243`）也允许从 failed 切换到生成并创建新任务，没有关联旧未知调用核对；此路径只作代码确认，未独立复现。
- 建议：在领域服务统一校验素材关联的运行任务、未知 attempt 和未解决核对记录，覆盖重试、切换来源、重新审批等所有入口；不要只补某一个按钮。
- 关闭条件：有 unresolved unknown 时所有付费入口一致拒绝；合法解除后只创建一次新任务；保留旧账本。增加 editor/reviewer、迟到结果及并发请求测试。

### A02 · P1 · “人工上传”被内容审批改成 AI 生成【复现】

- 证据：`contentflow/workflow.py:16` 的素材任务构造；`contentflow/routers/contents.py:278`。
- 原因：审批时只单独处理搜索和 configured 占位 provider，其余直接采用全局 image/video provider，未保留 per-asset 的 manual 选择。
- 复现：Asset.provider=`manual`，全局 image_provider=`http`；审批返回 200，Asset 变为 http/queued，并出现 1 个 `asset.generate` Job。没有运行 Worker 或调用供应商。
- 影响：违背用户明确选择，可能造成非预期素材生成费用。原人工素材测试把全局 provider 也设成 manual，没有覆盖此组合。
- 建议：显式来源优先，只有 configured 占位才解析运行配置；manual 必须进入 awaiting_upload。
- 关闭条件：manual/generate/search/hybrid × 全局 provider 的矩阵通过，人工模式产生 0 个 AI 生成任务。

### A03 · P1 · 模型的字符串 `"false"` 被当成审核通过【复现】

- 证据：`contentflow/content_agent.py:63` 使用 `bool(review.get("passed", False))`；`workflow_service.py:213` 使用该结果决定 blocked/needs_review。
- 复现：传入 `{"passed":"false","risk_level":"low","quality_score":9}` 后，归一化 passed 为 True。
- 影响：不规范模型输出可能使机器审核失败被显示为通过，并抑制应有改写。**人工审批仍存在，不等于自动公开发布。**
- 更广泛问题：文本 provider 只要求顶层 JSON object，缺少各阶段严格输出 schema；评分还应拒绝非有限数值及不合法类型，而非宽松修复为可信分数。
- 建议：严格布尔、有限且有界的分数、必要字段及引用结构校验；不合格输出明确进入受控错误/人工检查，不默认放行。
- 关闭条件：`"false"`、`"true"`、数组、缺字段、NaN/Infinity 等均不能伪装成合格审核。

### A04 · P1 · 输入框中的未保存修改并不是“确认通过”的对象【代码确认】

- 证据：`web/app/contentflow-app.tsx:2643` 的 decide 只提交 decision/reason/selected.version；`:2763` 表单使用 defaultValue；`:2840` 审批按钮是 type=button，直接调用 decide。
- 场景：用户修改正文但未点保存，直接点击确认通过。审批调用不会提交输入框正文，也没有 dirty 检查；批准的是服务端已保存版本，而非眼前改过的文本。
- 影响：用户可能以为修改生效并据此批准，实际旧稿进入素材和后续发布流程。切换条目或视图还会卸载未保存表单。本轮未在真实稿件上操作或跑浏览器端到端复现。
- 建议：有未保存改动时禁止审批并明确提示；或提供原子“保存并提交审核”，保存成功取得新版本后再确认。离开表单提示未保存状态。
- 关闭条件：浏览器实测“编辑→直接审批”“保存失败→审批”“切换稿件”“并发版本变化”，确保所见、所存、所批一致。

### A05 · P1 · 生成请求缺少业务入口幂等【复现】

- 证据：`contentflow/routers/runs.py:91`，每个请求创建新的 WorkflowRun；Job 幂等键依赖新 run.id，而非用户同一次生成意图。
- 复现：相同 campaign、相同请求体，甚至附相同 `Idempotency-Key`，两次均 202，产生 2 个不同 run。仅在隔离夹具关闭缺省 Prompt 治理依赖来测试入队，没有更改真实治理，也没有运行生成。
- 影响：请求重放、客户端重发或多端重复操作可创建多次收费任务。按钮 busy 与队列内部去重不能代替 HTTP 业务入口幂等。
- 建议：支持 workspace 范围客户端操作 ID、请求摘要与唯一约束；同键同请求返回原结果、同键异请求 409；同时限制用户/工作区排队量。
- 关闭条件：串行和 PostgreSQL 并发重放只产生一批任务；故意“再次生成”必须使用新的意图 ID。
- 边界：发布入口已有 request_id 和部分幂等设计，不能把此结论泛化为所有入口都完全没有幂等。

### A06 · P1/P2 · 人工改稿后仍显示旧文本的 AI 通过结论和评分【复现】

- 证据：`contentflow/routers/contents.py:155` 起的 update_content；前端 `contentflow-app.tsx:2607`、`:2789`。
- 复现：v1 有评分 9 / model passed=true，正文完全改写保存为 v2 后，status 正确回到 needs_review，但上述旧结果仍保留。前端直接显示该评分，未说明已过期。
- 影响：人工审批本身已清空，这是正确的；缺陷是机器审核证据未绑定版本，会误导审核者。
- 建议：保存时失效化旧审核并明确标记所属内容版本；重跑确定性规则，模型复审应独立选择和计费，不暗中调用。
- 关闭条件：新版本绝不展示无版本提示的旧评分/通过结论，历史仍可查看；最终审批清楚对应当前已保存文本。

### A07 · P1 · Worker 丢失租约后缺少逐调用停止边界【代码确认，故障影响待验证】

- 证据：`contentflow/worker.py:270` 心跳维护 lost；`:2143` 在整个 handler 返回后才判断；`provider_invocations.py:38` 的上下文只有 job/workspace，没有租约 attempt；`workflow_service.py:99` 的进度提交不校验执行租约。
- 现有保护：最终 complete_job 有 worker/attempt 校验，已有测试证明旧 Worker 不能完成新领取的 Job。不能说“没有心跳/没有 fencing”。
- 缺口：handler 未接收丢租约后的取消信号；一轮包含多个模型请求时，心跳先失效，不会自动阻止后续新请求及独立进度提交。最终回滚不能撤销已发出的费用/外部动作。
- 建议：每次外部调用、关键状态写回检查租约与 attempt；尽力取消尚未发出的请求。已经发出的请求仍按未知结果协议核对，不声称 exactly-once。
- 关闭条件：真实 PostgreSQL 故障注入覆盖心跳失败、网络恢复、旧 Worker 迟到；失去所有权后不发新调用、不覆盖新进度，保留迟到结果证据。

## 3. 影响稳定性和内容质量的主要欠缺

### A08 · P2 · 多标签页刷新会话可能相互踢下线【服务端行为复现，浏览器场景待验证】

`web/lib/contentflow-api.ts:34` 的 refreshPromise 只在当前页面实例生效；后端 `routers/auth.py:495` 对历史 refresh token 立即撤销整段会话。两个已携带同一旧 Cookie 的刷新请求依次处理时，实测结果为 200、401，随后 session=401。令牌重用检测本身是正确安全措施，不能简单删除。应加跨标签页刷新协调，并设计严格有界的并发处理；用双标签页到期测试验证，而非放宽任意旧令牌可用。

### A09 · P2 · 排队时选定的 Prompt 版本未冻结【代码确认】

`runs.py` 保存 Brief/style 快照，但没有保存本次选择的 Prompt release/hash；`workflow_service.py:76` 执行时重新读取 active release。排队期间切换 active 会令任务采用另一版本。Worker 会重新检查评测门禁，所以这不是绕过治理；问题是意图、复现和版本归属。应同时冻结 release、模型/参数与所需配置摘要，执行时校验完整性，并明确撤销版本对已排队任务的处置策略。

### A10 · P1/P2 · RAG 有召回，但事实可靠性仍不足【代码确认 + 同日验收记录】

- `knowledge_service.py:133` 只按近邻取前 6 条，没有相关性阈值/拒绝召回。库里只有无关文档也会返回；同日真实稿确实召回了无关合成保温杯资料，正文当次正确忽略了它。
- `workflow_service.py:230` 的 source_chunk_ids 保存所有召回项，不代表作者实际使用、逐事实引用或核实过的来源。
- 建议：相关性拒绝、必要时关键词/语义混合检索与重排；分开存 retrieved / used / verified；检查引用 ID 必须属于候选上下文；加入文档有效期、事实冲突与“资料不足”的明确路径。
- 验收不只看召回率：用无关库、空库、过期价格、互相冲突资料、带恶意指令资料测试内容事实和拒绝行为。重排并不是替代这些规则的万能修复。

### A11 · P2 · Embedding 模型兼容与批处理缺少产品级约束【代码确认】

- 知识块保存 embedding_model，但检索 SQL 和 SQLite 分支都不按模型/索引版本过滤。同为 1024 维不意味着向量空间兼容；切换服务/模型后旧向量可能被静默混用。
- `knowledge_service.py:80` 将整份文档 chunks 一次交给 encode_many；API provider 在 `embeddings.py:196` 整批发送。20MB 上传允许量并不等于供应商输入上限或 512MiB Worker 的安全索引量。
- 建议：明确模型/版本/维度索引身份；切换须重建并原子切换。按 token、条目和字节批处理，持久化进度、设置索引预算。尚未做最大文件 OOM/供应商限制实验，不把风险写成已发生崩溃。

### A12 · P1/P2 · 有用量账本，没有充分的费用与资源硬门禁【代码确认】

文本请求 `providers.py:426` 未提供输出 token 上限，`:461` 无边界地读取响应；生成入口缺少每用户/工作区任务预算。认证限流、存储配额和单轮改写上限已经存在，但不能控制文本费用、队列洪峰和大输出。应加请求输出/输入边界、队列与并发配额、预算预留/结算、供应商限流适配；超时未知费用仍按风险处理，不能当作零花费。

### A13 · P2 · 内容质量仍主要依赖同一模型自评，Eval 覆盖偏窄【代码确认 + 验收记录】

`content_agent.py:137` 仅在未通过或低于目标分时改写，达到 8 分但含高优先级修改建议仍可能直接结束；同日稿件评分 8.2、零改写且仍有具体表达问题。六例 fixture（`deploy/private-test/acceptance_fixture.py:36`）主要验证字段、若干关键词/禁用回显及审核真假值，不能证明持续写出有说服力的社媒内容。

建议建立版本化真实任务集：不同产品/受众/平台、资料稀缺和冲突、品牌风格、反例、结构与事实引用、封面准确性；以人工盲评通过率、事实错误率、人工改稿量、时延/成本为核心，并比较不同 Prompt/模型。高优先级修改应结构化为阻断项或明确接受的建议。没有必要把“更像 Agent”变成无界自主循环或不断叠加模型调用。

### A14 · P2 · 未知账单的人工处置选项不够诚实完整【代码确认】

`schemas.py:545` 对 retry 和 abandon 均强制 provider_checked=True；`routers/jobs.py:375` 固化记录。这不能准确表达“供应商无法查询，我接受风险重做”和“放弃任务但费用仍未知”。应分离供应商已核实、用户接受重复风险、放弃继续执行三种事实，保留 unknown 财务状态与证据。不能用伪造已核对来让界面更顺。
