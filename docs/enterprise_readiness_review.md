> 复审日期：2026-08-09
>
> 复审分支：main
>
> 工作区状态：存在未提交修改，本次复审不执行 reset、checkout、覆盖、暂存、提交或推送。
> 评审性质：基于当前源码、迁移、测试、Compose、运维文档和既有本地验收证据的企业就绪度审计。

## 1. 结论摘要

ContentFlow 已经具备完整的内容营销业务闭环、PostgreSQL/pgvector、对象存储、数据库任务队列、人工审核、平台适配器、RBAC、审计、备份恢复和容器化交付，不再属于玩具 Demo。

当前更准确的成熟度定位是：

- 已达到“可部署产品基线”；
- 尚未达到“可承载真实生产流量的生产就绪系统”；
- 距离“成熟企业完整项目”还缺少高可靠一致性、企业身份体系、AI 治理、数据治理、自动化交付、SRE 运营、安全合规和组织流程等体系化能力。

成熟企业项目的差距不只体现在代码功能，还体现在是否能持续回答以下问题：

1. 外部调用成功但本地提交失败时，如何保证不会重复发布？
2. 一个 Worker 执行超过租约时，如何防止其他 Worker 重复领取？
3. 账号、令牌、平台凭据和上传文件如何满足企业安全策略？
4. 如何证明模型升级、Prompt 修改和知识库变化没有降低内容质量？
5. 如何自动发布、回滚、告警、审计、灾备和处理线上事故？
6. 如何满足租户隔离、数据留存、删除、导出、合规和成本配额要求？
7. 谁拥有服务、谁批准变更、谁响应故障、哪些证据允许上线？

- L1：功能 Demo，主要证明流程可运行；

## 3. 已确认的项目优势

1. 当前 Web 主链路真实走 FastAPI、SQLAlchemy、数据库 Job 和独立 Worker。
2. 核心业务对象均持久化，工作流状态、内容版本、素材和发布任务可追踪。
3. 人工审批是外部发布前的强制门禁，不把模型审核当最终批准。
4. PostgreSQL 使用 SKIP LOCKED 领取任务，具备重试、租约和幂等键。
5. 平台凭据独立加密，支持历史密钥回退，审计元数据递归脱敏。
6. 生产配置拒绝 SQLite、本地对象存储、弱密钥、通配 CORS 和未显式允许的 Mock。
7. 已有 PostgreSQL、pgvector、MinIO、API、Worker、Web 联合部署和恢复验证。
8. 文档对 Mock、真实 Provider 和平台授权边界描述相对诚实。

这些能力构成了继续企业化的可靠基础，但不能替代下面的生产门禁。

## 4. P0：真实生产流量前必须解决

### ENT-P0-01：长任务没有租约心跳

原始发现证据（修复前）：

- contentflow/settings.py 中 Worker 默认租约为 300 秒；
- contentflow/job_queue.py 只在领取任务时写入 locked_at；
- contentflow/worker.py 在整个 handler 执行期间没有续租。

风险：

- 文本生成、媒体生成、下载或外部发布超过租约时，另一个 Worker 可以重复领取；
- 可能产生重复素材、重复模型费用和重复外部发布。

验收标准：

- Worker 周期性续租，并以 worker_id 和当前 attempt 做条件更新；
- 续租失败时停止继续产生外部副作用；
- 增加双 Worker、长处理时间和 Worker 失联的 PostgreSQL 集成测试。

### ENT-P0-02：外部发布缺少恰好一次和对账机制

原始发现证据（修复前）：

- contentflow/worker.py 先调用 connector.publish，再写 external_id 并提交数据库；
- 内部 idempotency_key 没有形成外部平台级幂等协议；
- 抖音和公众号没有通用发布回调、状态轮询和定期对账任务。

风险：

- 平台成功、本地事务失败或进程退出时，重试可能重复创建作品；
- 本地状态可能是 failed，平台实际已经发布；
- 公众号 submitted 不等于最终发布成功。

验收标准：

- 建立发布 Outbox/状态机，持久化外部请求标识；
- 能使用平台幂等键时必须传递，不能使用时必须先查询和对账；
- 为 unknown/reconciling 状态建立人工处置和自动对账；
- 对“成功后崩溃”“超时但平台成功”“回调重复”建立测试。

### ENT-P0-03：并发编辑和审核没有乐观锁

原始发现证据（修复前）：

- contentflow/routers/contents.py 更新时直接执行 item.version += 1；
- API 没有 expected_version、If-Match 或 SELECT FOR UPDATE；
- 审核接口也没有确认审核的是客户端看到的版本。

风险：

- 两个编辑者同时保存会发生覆盖或版本冲突；
- 审核员可能批准编辑过程中已经变化的内容；
- ContentRevision 唯一约束可能把并发冲突表现为 500。

验收标准：

- PATCH 和审核请求必须携带 expected_version；
- 使用条件 UPDATE 或行锁，冲突返回 409；
- 审核记录绑定精确内容版本；
- 增加并发编辑、编辑与审核竞争测试。

### ENT-P0-04：账号和浏览器会话不满足企业安全要求

证据：

- access token 默认有效 480 分钟；
- 没有 Refresh Token、jti、撤销列表、密码重置、MFA 或企业 SSO；
- Web 将 Bearer Token 保存在 localStorage；
- Web 安全响应头没有 Content-Security-Policy；
- 登录/注册限流仍依赖外部网关。

风险：

- XSS 可以长期读取并带走访问令牌；
- 令牌被盗后无法单独撤销；
- 暴力破解和撞库无法由应用集群统一控制。

验收标准：

- 优先采用 OIDC/SAML 企业身份源，或实现短期 Access Token + 旋转 Refresh Token；
- Refresh Token 使用 Secure、HttpOnly、SameSite Cookie；
- 建立 jti/会话撤销、密码重置、MFA 和登录异常审计；
- 部署 CSP，并使用 Redis 等共享存储实施 IP、账户和租户限流。

### ENT-P0-05：真实模型、平台和 RAG 质量尚未签收

证据：

- docs/production_requirements.md 仍把真实 外部模型/媒体 Provider、抖音、公众号和 RAG 评测列为未完成；
- 公众号指标接口和小红书自动指标能力仍明确未实现；
- 当前自动测试主要使用 Mock Provider 和连接器 MockTransport。

风险：

- 无法证明真实租户的 schema、权限、限流、错误码、费用和媒体过期行为；
- 无法证明知识召回和生成事实准确性达到业务要求。

验收标准：

- 使用独立测试租户完成真实调用矩阵；
- 保存脱敏请求/响应 schema、错误码、时延、费用和平台审核结果；
- 建立带标准答案的 RAG/生成评测集并定义上线阈值；
- Provider 或 Prompt 变更必须经过回归评测。

### ENT-P0-06：备份不具备完整一致性和对象级完整性

证据：

- PostgreSQL dump 有 SHA-256；
- MinIO 镜像只在 manifest 中保存 file_count；
- 数据库 dump 与对象镜像不是统一时间点的一致性快照；
- 没有 WAL/PITR、自动保留和异地复制的仓库实现。

风险：

- 对象损坏但数量不变时恢复校验仍可能通过；
- 数据库引用与对象版本可能错位；
- 无法满足明确的 RPO/RTO。

验收标准：

- manifest 保存每个对象的 key、版本、大小、ETag/校验和；
- 明确暂停写入或采用可证明一致的快照方案；
- PostgreSQL 启用 WAL 归档/PITR；
- 备份自动调度、加密、异地保存并定期恢复演练；
- 用演练结果确认 RPO、RTO。

### ENT-P0-07：生产入口和密钥基础设施未交付

证据：

- 当前 Compose 直接暴露 API、Web、PostgreSQL 和 MinIO 控制台端口；
- 没有仓库内的 TLS 网关、WAF、共享限流和集中密钥管理部署；
- 凭据主密钥仍通过环境变量注入。

风险：

- 单机 Compose 不能代表安全互联网入口；
- 多副本密钥轮换、审计和访问控制缺少企业级控制面。

验收标准：

- 生产流量通过 TLS 网关/WAF；
- 数据库和对象存储管理面不直接暴露公网；
- 密钥来自 KMS/Vault/云 Secret Manager，并有访问审计和轮换；
- 建立独立 dev/staging/prod 配置和权限边界。

## 5. P1：达到企业生产标准前应完成

### ENT-P1-01：多租户隔离只有应用层过滤

当前大部分查询都正确携带 workspace_id，但 PostgreSQL 没有 RLS 或租户 Session Context。任何遗漏过滤条件的未来查询都可能跨租户读取数据。

建议：

- 为核心表增加 PostgreSQL RLS；
- 每个事务设置当前 workspace_id；
- 增加跨租户属性测试和恶意 IDOR 测试；
- 对对象存储 key、备份和日志同步执行租户隔离策略。

### ENT-P1-02：审批不具备职责分离

角色采用 viewer < editor < reviewer < admin 的继承关系，因此 reviewer/admin 可以编辑后再批准自己的内容。系统没有 maker-checker、双人审批或高风险内容升级策略。

建议：

- 审核时禁止 approved_by 等于最近 changed_by；
- 支持按品牌、平台和风险等级配置单人/双人审批；
- 高风险内容必须由合规角色批准；
- 将审批策略和每次决策版本化。

### ENT-P1-03：审计日志不是不可篡改账本

AuditLog 是普通数据库表，没有哈希链、签名、WORM 归档、留存任务和标准导出。工作区删除的级联策略还可能删除相关审计证据。

建议：

- 审计事件增加前序哈希或批次签名；
- 定期写入独立不可变存储；
- 定义留存期、检索、导出、法律保全和清理策略；
- 对管理员和平台凭据操作增加更详细的安全审计。

### ENT-P1-04：上传文件信任客户端 MIME

素材上传只检查 file.content_type 前缀，知识文件主要检查扩展名；没有 magic-byte 检测、恶意文件扫描、隔离区和内容清洗。

建议：

- 服务端识别真实文件类型；
- 上传先进入 quarantine bucket；
- 集成恶意软件扫描和解压炸弹保护；
- 对 SVG、HTML、JSON、压缩包和媒体解析器建立明确策略；
- 大文件下载改用短期签名 URL，避免 API 进程整块读取。

### ENT-P1-05：模型与 Prompt 治理不足

Prompt 直接硬编码在 contentflow/prompts.py；WorkflowRun 只记录 provider 和结果，没有完整记录 model revision、prompt version、参数、token、费用、时延和评测版本。

建议：

- 建立 Prompt Registry 和不可变版本号；
- 每次运行保存 provider/model/prompt/参数/知识版本；
- 记录 token、费用、时延和 Provider request_id；
- 建立 Prompt 注入防护、PII 检测、版权和敏感内容政策；
- 模型升级必须通过离线评测和小流量发布。

### ENT-P1-06：外部调用韧性不足

各 Provider/Connector 主要配置固定 timeout 并直接 raise_for_status，没有统一的重试分类、Retry-After、指数退避、连接池、熔断、并发隔离和供应商降级。

建议：

- 区分可重试和不可重试错误；
- 尊重 429/Retry-After；
- 使用带连接池和指标的共享 HTTP Client；
- 按 Provider/租户建立并发限制和熔断器；
- Worker 已支持 SIGTERM/SIGINT 优雅排空；继续补停机超时指标、强制终止告警和编排层 termination grace 验证。

### ENT-P1-07：自动测试仍偏本地和 SQLite

## 14. 2026-08-08 第四轮复审：自动发布对账与成熟度再评估

### 14.1 本轮关闭和部分关闭的风险

1. 微信 submitted 永久悬挂：提交成功后现在创建 `publish.reconcile` Job，Worker 也会补扫历史 submitted 记录；依据[微信公众号发布状态查询](https://developers.weixin.qq.com/doc/offiaccount/Publish/Get_status.html)调用 `freepublish/get`。
2. 假阳性发布：连接器不依据不稳定的数字状态猜测成功；只有响应包含 `article_id` 才将领域状态写为 published。
3. 慢外部请求持锁：自动对账采用两阶段事务，远程 HTTP 前释放 PublishJob 行锁，返回后重新锁定并验证状态和查询键。
4. 人工与自动竞态：reviewer 可接管 submitted/reconciliation_required，并原子终结自动对账 Job；迟到自动结果只写 `publish.reconciliation_stale_ignored`，不覆盖人工决策。
5. 分发结果与补偿任务崩溃窗口：submitted 远程结果和后续对账 Job 先在同一事务中持久化，原 publish.dispatch 队列任务在下一提交中完成；重放读取领域终态而不是再次发布。
6. 二次分发永久悬挂：人工确认未发布后再次得到新 `publish_id` 时，旧 succeeded/failed 对账 Job 现在会原位复活并清空旧结果/租约/尝试次数；自动最终 published 也会收敛仍 running 的原分发 Job。

## 21. 2026-08-09 第十一轮复审：平台渠道入口契约

### 21.1 新发现与修复

抖音渠道创建入口过去只要求 `access_token`，而连接器执行测试、发布和指标回收时都要求 `access_token + open_id`；公众号只校验字段名存在，空白 App ID/Secret 也可进入数据库。该差异会把可同步发现的配置错误推迟到 Worker，增加无效任务、排障成本和敏感配置反复操作。

### 21.2 成熟度与边界

当前对个人本地使用的核心业务风险进一步降低：误传过量证据或长期内容改版不会再让关键发布事务扫描无限集合，旧素材任务也不会继续产生无效 Provider 请求。要达到公开测试，仍需工作区总资源/成本防滥用、邀请/恢复/删除与法务流程、浏览器 E2E 和容量/SLO；要达到成熟企业产品，还必须补数据库纵深隔离、企业身份与职责分离、受管密钥/不可变审计、PITR/异地容灾、正式发布治理和多平台长期生产证据。

## 40. 2026-09-03 第三十轮复审：统一存储账本后的成熟度差距

### 40.1 复审结论

第二十九轮的最高优先级缺口“工作区物理存储没有统一账本”已经实质关闭：所有当前持久对象写入共享同一套并发预留、正式计费、事务补偿、可重试删除和有界对账协议；管理员能看到用量与异常，旧共享 URI 会被保守隔离。存储可靠性因此进入较强 L2-L3 基线，但这仍不是完整数据生命周期、云成本治理或规模化对象平台。综合成熟度继续评为 L2+，项目已明显超出玩具 Demo，但尚未完成企业生产签收。

### 40.2 本轮关闭或部分关闭的风险与证据

| 维度 | 当前提升 | 当前证据 | 未关闭边界 |
| --- | --- | --- | --- |
| 并发配额 | 工作区字节/对象数原子预留，成功后转正式计费，回滚补偿物理对象 | SQLite 状态机；CI #33679198143 以真实 PostgreSQL/MinIO 完成 292 项测试、覆盖率 81.62% | 无租户成本预算/账单核对 |
| 删除可靠性 | `storage.delete` 幂等重试，失败继续计费，成功只释放一次 | 删除失败/重试、素材替换、脚本过期和跨工作区 URI 回归 | 通用保留、归档、合法删除、备份传播未实现 |
| 一致性巡检 | 分页核对缺失、大小漂移、过期预留和孤儿；新对象有扫描水位保护 | local 专项、MinIO 分页测试已入仓 | 无周期调度、告警到人、全对象内容哈希和百万对象预算 |
| 旧数据安全 | 重复旧 URI 标记共享完整性异常并拒绝自动删除 | 迁移集合检测与运行时隔离回归 | 需人工拆引用/复制迁移，旧未知大小会阻断新增写入 |
| 管理可见性 | 用量/异常 API 和管理工作台；孤儿清理二次确认 | API 权限/筛选/任务去重、lint/build/SSR | 未做真实管理员浏览器 E2E、指标面板和自动处置审批 |

### 40.3 当前仍存在的 5 个不足

1. **数据生命周期只覆盖部分删除触发点**：素材替换和脚本过期已有可靠删除，但知识、发布证据、活动、内容和工作区没有统一保留、归档、导出、合法删除、legal hold 及备份副本删除传播。
2. **存储对账尚不可规模化运营**：当前只扫描正在配置的 local 或单一 Bucket，由管理员手动触发；没有周期计划、Prometheus 指标/告警、百万对象分片预算、内容哈希抽检、跨后端清点和云账单核对。
3. **数据库仍不是独立租户安全边界**：账本隔离依赖应用传入 workspace；owner/migrator/API/Worker 角色未拆分，核心表没有 FORCE RLS。该高影响权限迁移继续等待单独授权与恢复演练。
4. **产品历史体验与前端维护性仍不足**：登录仍可能追取各域最多 2000 条，缺按需历史、搜索/导出/虚拟列表；大型工作台单文件、8 路活动轮询和缺少浏览器 E2E/请求预算仍会放大变更风险。
5. **企业信任与真实运营证据未闭环**：OIDC/SAML、MFA/step-up、SCIM、受管 KMS、外部不可变审计、PITR/异地、目标云多副本/SLO，以及公众号完整异常矩阵和其他平台长期运行尚未共同签收。

### 40.4 可以继续改进的 5 个方向

1. 建立跨 Knowledge/Asset/Evidence/PublishJob/Content/Workspace 的数据生命周期策略：保留期、归档、用户导出/删除、legal hold、审批、备份删除传播和可复核完成证据。
2. 将 `storage.reconcile` 接入受控周期调度和 Prometheus/告警，增加分片/速率预算、哈希抽检、旧后端 inventory、S3 版本生命周期与云账单差异核对；先用故障注入验证不会误删。
3. 在明确高影响授权后，以当前 head 联合备份恢复为前置，拆分数据库角色并分批启用 FORCE RLS，增加 API/Worker 租户上下文、真实 PostgreSQL 跨租户负向测试和 break-glass 审计。
4. 实现独立历史页面、服务端组合筛选/导出和虚拟列表，拆分领域 query hooks/组件/错误边界；用 Playwright 固定首次、活动、隐藏和断线恢复的请求预算，再评估 SSE/Inbox。
5. 并行推进 OIDC + MFA/step-up、SCIM、KMS/Secret Manager、外部 WORM/SIEM 审计锚点、PITR/异地、OTel/SLO/容量演练和真实公众号异常矩阵；抖音账号未就绪前继续保留未签收状态。

### 40.5 距离不同交付层级还差什么

- **个人本地部署使用**：统一存储配额和删除/核对让磁盘使用比上一轮更可控；仍需用户维护 Provider/微信凭据与白名单、定期备份/核对、处理共享旧对象和版本升级。已经可用，但不是零运维产品。
- **个人公开部署**：仍按用户要求冻结。恢复时需固定公网出口、域名/TLS/WAF、Secret Manager、托管 PostgreSQL/对象存储、备份恢复、监控告警、升级回滚和真实公网验收；不能仅把本地栈放到 Vercel/GitHub Pages。
- **公开测试**：还需邀请/账号恢复、滥用与 AI/媒体/存储成本配额、隐私告知、导出/删除、客服/事故入口、浏览器 E2E、容量与 SLO，以及持续漏洞与平台异常处置。
- **成熟企业商业项目**：还需数据库纵深隔离、企业 IAM/职责分离、受管密钥和不可变审计、完整数据生命周期、HA/PITR/异地、正式 SRE/FinOps、受保护镜像晋级/回滚、合规法务/供应商/SLA 和多平台长期生产证据。当前仍是可靠且可持续交付的产品基线，不是企业完成态。

## 41. 2026-09-03 第三十一轮复审：自动存储核对与主动运维

### 41.1 复审结论

第三十轮的“存储核对只靠管理员记得点击”已实质关闭：当前 Worker 会以多副本安全方式周期安排只读核对，失败不会热循环，Prometheus/Grafana 能主动暴露完整性异常、核对超期/失败和删除积压。到期选择也有独立数据库索引。存储子系统由“有账可查”推进到“能周期发现并告警”，局部达到较强 L2-L3 运维基线；但通知到人、百万对象容量、全生命周期和目标环境长期 SLO 仍未签收，综合成熟度继续评为 L2+。
