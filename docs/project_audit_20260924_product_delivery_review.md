## 1. 结论

**ContentFlow 已有真正的产品工程基础，但目前更适合开发者陪同的受控私测，尚不是可交给普通用户长期独立运行的完整成品。** 当前主要差距是：产出是否有效、成果是否保留、费用是否有界、信息是否安全，以及故障后能否恢复；不是继续增加页面或平台数量。

本轮没有确认匿名接管、远程代码执行或跨陌生租户访问的 P0 利用链，也没有证明这些风险已经被排除。P1/P2 是本项目整改优先级，不是 CVSS 分数；历次 A 编号不是仍开放的安全漏洞数量。

## 3. 新增发现

### A55 / P1（公开服务前）：异常日志可能复制私密业务字段

**位置：** `contentflow/api.py:230–241` 将原异常及 traceback 传给 logger；`contentflow/db.py:29` 创建引擎未设置 `hide_parameters`。普通审计 metadata 的脱敏和 HTTP 响应脱敏不覆盖此通道。

**复现：** 在临时库中向同一个发布任务、同一 captured_at 再次录入指标，在 raw 中附合成私密业务标记。数据库唯一约束报错，实际 API 返回 500。启用应用 logger 后，捕获的异常日志约 9 KB，包含 SQL parameters 及合成标记；返回响应不含该标记。

**重要条件：** 开发态自动迁移会关闭此 logger（A56），因此第一个探针未捕获日志。第二个探针仅在测试进程启用 logger，再复现原业务请求和原异常处理路径；不是修改 SQL、伪造异常或发现线上已泄密。生产启动不执行开发迁移，不能把“开发 logger 被关闭”当成保密措施。

**影响：** 内容、指标 raw 等字段可能被额外复制到权限、保留周期不同的日志系统。需要有写入权限的请求触发异常；本轮未证明凭据存储解密或陌生用户读取日志。重复指标返回 500 本身也说明冲突契约尚不完整，归入 A33 的修复范围。

**关闭条件：** 统一安全异常记录；SQL 参数默认隐藏，但不能只靠这一项，因为原始异常文本也可能携带载荷。保留 request_id、异常类型和可定位堆栈，不输出原文秘密。加入 SQL 约束错误、网络错误、嵌套异常及采集端日志回归；重复指标明确返回冲突/幂等结果，而不是未处理的 500。

### A56 / P2：开发启动迁移会关闭已有应用日志

**位置：** `migrations/env.py:15` 调用 `fileConfig(config.config_file_name)`；开发 API lifespan 在 `contentflow/api.py:78` 执行迁移。没有显式保留已有 logger。

**复现：** 全新测试进程中创建应用并完成开发态 lifespan 后，`contentflow.api` logger 的 `disabled` 为 true；正常异常捕获无日志。手动启用该 logger 后，相同错误可被捕获。

**影响与边界：** 本地开发/嵌入式迁移路径可能缺失请求和错误日志，增加排障难度。没有证明不执行迁移的生产进程也会被关闭。不能用永久关闭日志来“修复”A55。

**关闭条件：** 明确迁移与应用日志配置所有权；开发/生产启动及管理员入口均验证日志仍可用，且同步通过 A55 的敏感信息回归。

## 4. 亟需修复的交付阻断项

### A12：费用与资源没有完整硬边界

- `providers.py:440/475` 没有输出 token 硬上限，整体读取模型响应；`knowledge_service.py:80` 把所有分块交给一次 Embedding；`schemas.py:255–261` 的若干列表缺少数量/元素长度限制。
- 已有登录限流、对象配额、有限改写次数，但缺工作区模型预算、Provider 并发、积压和输入/输出硬限制。合法账户误操作也可触发，不必先有黑客。
- 新 schema readiness 每次反射结构并检查存储，公网 Caddy 又转发匿名 `/health/ready`。需评估健康检查开销、出网调用及边缘速率限制；未做负载攻击，不声称已导致生产拒绝服务。逐 SQL timeout 不等于整个请求总时限。
- 验收应证明：预算不足时不会发出调用；未知结果不释放预算后自动重放；大文档按批处理；异常大响应不会耗尽内存；单工作区不能挤占全部队列。

### A39/A40：素材有效性和最终载荷审核缺口

- A39：实际 HTTP 媒体结果解析 → 实际 `asset.generate` Worker → 本地存储，`b"not an image"` 得到 `asset=ready / job=succeeded / bytes=12`。见 `media_providers.py:874`、`worker.py:989`。人工上传/搜索部分已有图像校验，缺统一入口，不是全项目完全不校验。
- A40：禁词只放 hashtags 时 passed=true，移入正文则 false；`review.py:34` 只扫标题/正文，`review_evidence.py:122` 重新审核也只传二者。绑定了版本，不等于该版本每个发布字段都被检查。
- 修复应统一实际解码、MIME/尺寸/像素/时长/体积门禁，以及最终发送/导出的标题、正文、标签、CTA、脚本等适用字段。不能靠 MIME 标签或模型评分替代，也不要绕过现有人工批准。

### A47：后续平台失败会丢掉已完成的可编辑稿

- `workflow_service.py:192–210` 全部平台先进入内存结果集，再创建 ContentItem。
- 实际 Worker 完成第一平台后，对第二平台注入超时，得到 `run=failed / contents=0 / result_keys=[ai_provenance]`。调用诊断还在，不能说所有证据丢失；但第一篇稿件确实无法继续编辑。
- 必须按平台/阶段持久化检查点，支持明确的部分成功及安全续作，并绑定输入/Prompt/模型身份。不自动重放结果未知的调用。

### A41/A51/A52/A53/A54：本地实现不等于实际交付

保留现有修复，完成同版本真实 PG/MinIO、锁竞争、PUT 回执丢失、进程中止、staging 回收及迁移/恢复演练。前阶段的 59 项 skip 仍不能签收。

部署脚本已验证 API/当前容器 Worker，但 `deploy.sh:105–136` 晋级前没有验证实际用户入口 HTTPS、Caddy 代理路径和 Web 版本。Compose 已有 `caddy → web healthy → api healthy` 依赖，不能误写“完全不检查 Web”；欠缺的是启动后的端到端入口验收、证书/路由失败和前后端错版回归。这是静态交付缺口，未用真实部署证明故障。

## 6. 使用体验和可维护性

使用 `web-design-guidelines` 技能并取得 [Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md)。以下为源码审查，不是新增浏览器/移动端/读屏验收。

- `web/app/contentflow-app.tsx:1315`：初始化批量等待约 22 组请求，指标独立降级，但其他不相关模块失败仍可阻断整批刷新。按页/角色加载、独立错误和局部重试。
- `web/lib/contentflow-api.ts:51` 与 `contentflow-app.tsx:1620`：最多读取 20×100 条，项目筛选主要在内存进行。提示“用筛选找历史”，却无法定位未加载的数据。应提供真实服务端筛选与分页、明确显示查询范围。
- `contentflow-app.tsx:1245/1281/1678`：视图/项目主要是 state 和按钮切换，没有完整的项目/稿件深链接与前进后退恢复。现有操作意图回执不等于业务草稿恢复。
- `web/lib/browser-session.ts:226`：普通业务 fetch 无统一截止；生成/发布和认证已有局部保护，不能说全都没有超时。读可取消重试，写超时必须保存未知结果，不能盲目重发。
- 页面应突出“当前项目、当前阶段、下一步动作、失败后怎么办”；把高级治理配置与日常内容操作分开。已有动画/进度提示需要配合真实状态、明确人工选择和无障碍验证。
- 六千行主页面和两千多行 Worker 提高跨状态修改成本。按事务、外部 I/O、领域状态、页面资源拆分，不能只挪文件；保留幂等/执行权/版本不变量回归。
- 文档历史状态过多。当前入口必须只有一处，记录候选源码、schema、实际部署及未过验收；历史报告保留但不继续叠加为“当前漏洞”。

## 7. 公开测试和企业交付还缺什么

这些是风险与验收缺口，不都属于已证实漏洞，也不要求个人私测立刻建设完整企业平台。

1. **秘密生命周期：** 公开前轮换曾在聊天中提供的凭据并核对撤销结果、日志/备份留存和访问范围。未证明第三方泄漏；本轮不擅自轮换。
2. **运行最小权限：** 公网 Compose 的 API/Worker 与 PostgreSQL 初始化使用同一 contentflow 身份。运行、迁移、备份角色应拆分，对象存储按作用限制；应用 workspace 过滤已有，但仍需真实角色/租户负向矩阵。RLS 是可选纵深，不是修复应用越权的替代品。
3. **联合恢复：** 当前 DB、向量、对象、配置/解密密钥的异机恢复、数据损失上限和恢复时间没有本批签收。恢复后还要验证不会重复发布；有 dump 脚本不等于可恢复。
4. **通知闭环：** `deploy/observability/README.md:50` 明确没有内置 receiver。需告警真正到人、分级、处置和恢复演练，不只展示图表。
5. **容量与长时运行：** 2 核 4G 的低并发测试可作为目标，但承载力仍需测量队列、内存、磁盘、长事务、断网/断电/重启和多日稳定性，不能靠一次跑通保证。
6. **账号与数据治理：** 按需求补账户恢复、会话管理/MFA或组织登录、撤权；数据导出/删除/保留、知识撤回向索引/衍生内容的传播及备份过期。企业再补职责分离和独立审计保留。
7. **可验证交付：** 当前源码对应 CI、真实服务、镜像/前后端版本、迁移兼容与回退责任、支持的平台/模型矩阵。在线依赖审计此前外发权限未解决，本轮不重跑或借 CI 绕过；旧扫描不能代替当前扫描。
