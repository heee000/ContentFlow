## 1. 总体判断

现在是一个具备真实产品工程基础、适合继续受控私测的项目，但不是可靠性和安全性已经验收完成的成品。主要差距不是缺页面或再接一个模型，而是：**一次操作的边界、费用与执行权控制、内容/素材/统计的真实性、故障后恢复，以及候选版本的交付一致性**。

本次没有确认匿名接管、远程代码执行或跨陌生租户读写等 P0；这不等于排除这些风险，也不是渗透测试认证。P1/P2 是整改顺序，不是 CVSS 分数。A01–A46 是历次编号，不代表仍有 46 个未修复安全漏洞。

不宜现在扩大到不可信用户公网测试。也不建议先增加更多平台、无上限 Agent 循环、微服务或 Kubernetes；这些不能解决下面已经复现的正确性缺陷。

## 3. 亟需整改的风险

### A05 / P1：同一次生成操作仍能创建多份任务【当前复现】

`contentflow/routers/runs.py:91/145/161`：同一个活动、相同请求体、相同 `Idempotency-Key` 连续请求，返回 **202/202、不同 run ID**。队列按新 run ID 去重，因此不能防住用户超时重试产生新一轮调用。本次没有真实计费。

修复/关闭标准：生成入口具有工作区范围的操作 ID、请求摘要和唯一约束；同请求重放原回执，异请求同 ID 返回冲突；明确“重新生成”才新建意图。必须覆盖回执丢失和 PG 同时提交，不只测按钮禁用。

### A07/A12 / P1：执行权与费用控制仍不完整【源码确认】

`contentflow/worker.py:2149/2155` 在 handler 执行后检查租约丢失；`provider_invocations.py:38` 的任务上下文没有 worker/attempt 代次。已有续租和队列最终提交保护，但不能保证旧 Worker 恢复后不会继续下一次外部调用或先更新领域状态。

`providers.py:438/473` 的文本请求没有输出 token 硬上限，响应整体读取；`knowledge_service.py:80` 一次提交全部知识分块；`schemas.py:236` 附近的若干数组未设元素数/长度上限。已有存储配额、认证限流、调用账本和有界改写轮次，不能据此宣称工作区费用/积压/并发已有总上限。

修复/关闭标准：调用前和领域写回检查执行代次；失租后不继续新调用；未知结果保留人工核对。增加输入/响应字节、分块批次、输出 token、工作区并发/队列/预算硬限制。用可控旧进程恢复和调用后提交失败验证，不承诺取消已经送达供应商的请求或通用 exactly-once。

### A39/A40 / P1：素材就绪和规则通过不等于实际发布物有效【当前复现】

- `media_providers.py:872` → `worker.py:864/958`：把 **12 字节 `not an image`** 声称为 `image/png`，经过实际解析、存储路径，Asset 变为 **ready**。检查了 base64/大小/MIME 标签，但没有统一验证实际图片字节。这不是“人工上传也完全没校验”；人工入口已有独立校验。
- `review.py:34`：禁用词在 hashtag，标题/正文不含该词，规则仍 **passed=true**。标签属于实际导出的内容字段；审核版本/hash 固定了对象，并没有自动补齐规则覆盖范围。

修复/关闭标准：生成、下载、人工素材共用解码/类型/尺寸/像素/大小门禁，视频另验容器/时长/编码；对实际发送的所有文本字段检查规则。将硬阻断与允许说明理由的人工例外分开，不靠 MIME 或模型自评替代验证。

### A41 / P1（交付门禁）：数据库能连接就被当成业务就绪【当前复现】

`api.py:283`：替换为没有任何表的内存数据库，`/health/ready` 仍返回 **200 / database=ok**。`worker.py:2445` 入口仍调用 `create_schema()`；创建 ORM 表不是验证 Alembic/pgvector/索引/约束同版。

修复/关闭标准：API/Worker 启动和就绪校验受支持迁移版本及必要 schema；迁移由独立升级步骤执行。缺迁移/错版本必须拒绝就绪，不能等第一笔业务请求报错。保留轻量 liveness，不将 readiness 改成付费模型探测。

## 4. 本轮新增和加深的正确性缺陷

### A44 / P2（事务边界）：队列冲突恢复会回滚调用者整笔事务【新增，受控复现】

`job_queue.py:32/59`：捕获唯一键冲突后调用 `session.rollback()`，然后查询已有 Job 并正常返回。它没有只回滚队列插入的局部事务。

本次临时数据库先保存已有 Job，再修改 Workspace 名称并 flush；受控模拟第一次查重没看到竞争者，后续 INSERT 触发真实 SQLite 唯一键冲突。结果：**返回已有 Job，但调用者此前名称修改丢失**。

证据边界：第一次 SELECT 未命中由探针注入，用来模拟并发窗口；没有声称已在真实 PG/生产业务中复现这次数据丢失。该帮助函数有多处调用，需逐条确认哪些入口锁已阻止竞争、哪些确实可达。

整改：定义清楚队列函数的事务所有权，使用局部冲突处理或由外层显式重试整笔事务；不能吞掉整笔回滚继续返回成功。新增真实 PG 两会话测试，验证领域修改、队列与审计一起提交或一起失败。

### A45 / P2：无效重生成范围会得到“待人工审核”，却没有内容【新增，当前复现】

`routers/runs.py:91`、`workflow_service.py:186/308`：仅含公众号的活动请求 `regenerate_platforms=["douyin"]`，接口 **202**；隔离执行后 run 为 **awaiting_review / human_review**，新增内容 **0 条**。

代码先检索并生成 plan，再取活动平台与请求平台交集。真实配置下可能已经耗费查询/规划调用，才发现没有要生成的平台；本次只用 Hash/Mock，没有实际费用。

整改：入队前验证请求平台非空且为活动平台子集、去重并冻结；明确“全部平台”的语义。无结果不应成功进入人工审核；覆盖活动空平台、重复平台、篡改排队参数及旧任务兼容。

### A46 / P2：生产禁用 Mock 只限制默认配置，调用覆盖值可绕过【新增，构造器复现+调用链确认】

`settings.py:404` 检查配置的默认 Provider；`text_generation.py:7/9` 接收 override 后直接返回 Mock；`routers/admin.py:1017` 的 Eval 请求也接受 mock，没有应用生产禁用策略。

使用全合成、已通过 `validate_runtime()` 的 **production + allow_mock_providers=false + 真实协议类型默认 Provider** 配置，`build_text_provider(settings, "mock")` 仍返回 **MockProvider**。没有建立 PostgreSQL/外部连接。

边界：这是运行策略一致性缺陷，不是匿名越权，也不是已证明 Mock Eval 能冒充真实模型 Eval——当前门禁仍匹配 Provider/模型。生产生成还依赖对应的治理/Eval 前置条件，不能说任意普通请求直接绕过所有门禁。

整改：实际 Provider 解析必须统一执行环境允许策略；在 API 入队与 Worker 执行两处拒绝不允许的 override。治理门禁继续区分 Mock 与真实结果。

### A16 / P2：晚提交的更新会被增量刷新漏掉【从源码风险升级为隔离复现】

`entities.py:40` 的更新时间发生在更新/flush；`pagination.py:155/163` 使用查询后墙钟作为同步时刻；`web/app/contentflow-app.tsx:709` 只回退两秒。

本次两个 SQLite 会话：写事务改活动名并 flush，等待三秒但不提交；列表读取看到旧名并返回同步时刻；之后提交写事务。下一次按“同步时刻减两秒”请求增量，返回 **200、0 条**；全量读取却能看到新名。

影响是页面可能持续保持旧状态，不只是慢几秒；手动全量刷新可以恢复。本次复现了服务端数据窗口和前端采用的算法，没有执行 PG 竞争或专门 UI 故障旅程。

整改：定义基于已提交变化的同步协议，包含删除/失效事件及补偿全量同步；单纯把两秒改成更大的固定数不是严格解决方案。覆盖长事务、同时间戳、分页期间更新和断线恢复。
