## 4. 新确认的问题

### A25 · P1 · 发布任务未冻结最终素材清单，低权限编辑可改变已排期封面【隔离复现】

- `routers/publishing.py:170–176` 只保存内容版本、模式、请求 ID 等，没有选中素材及 checksum 的清单。
- `routers/assets.py:381–510` 的 ready 候选切换允许 editor，既不改变正文版本，也不使已有发布任务失效。
- `worker.py:1298–1314` 分发时重新读取当前 selected，而不是当时 reviewer 确认的素材。
- 探针：reviewer/admin 基于封面 A 创建发布任务 → 将测试用户降为 editor → 选择同版本封面 B，HTTP 200 → 用录参连接器执行原任务：收到 B、没有 A，内容仍 v1/approved。没有连接微信，不能称实际公开误发。
- 影响：正文审批版本正确，也不能保证最终发布的封面经过发布者确认；这是工作区内的授权意图缺口，不是匿名越权。
- 修复：发布时冻结正文 revision、素材 ID/校验和/选用版本、必要渠道配置；素材变化要使待执行发布过期或需要重确认。内容/素材/发布临界区需统一设计，不能只补 UI 禁用按钮。
- 验收：排期后 editor 改选/补传、同版本对象替换、分发与改稿/选图并发，均不能静默改变已授权发布包。

### A26 · P1/P2 · 立即发布 API 的操作 ID 可省略，重放产生不同发布任务【隔离复现】

- `schemas.py:447` 允许 request_id=None；`routers/publishing.py:147–152` 缺省采用每次生成的 scheduled_at。
- 两次相同 `publish_now=true` 请求不带 request_id，均 202，得到不同任务 ID；没有执行这两条任务或调用平台。
- 正常 Web 目前在 `contentflow-app.tsx:3601` 传入 request_id，因此不能称正常页面每次点击都必然重发。问题是 API 契约没强制保护调用者，其他客户端或页面状态丢失的恢复容易出错。
- 修复：有外部写入的发布要求稳定操作 ID，绑定规范化请求摘要；同 ID 相同参数返回原任务，改变参数明确 409；补 PostgreSQL 并发和响应丢失重放测试，不以先查询再插入代替竞争处理。

### A27 · P2 · 素材 API 与下载 Worker 的行锁顺序相反【代码确认，PostgreSQL 死锁尚未实测】

- 新 `asset_operations.py:28–54` 用户入口先锁 ContentItem 再锁 Asset；审批也先锁内容。
- `worker.py:720–729` 下载结束写回仍先锁 Asset 再锁 ContentItem。
- 可能的竞争：API 持有内容锁等素材锁，Worker 持有素材锁等内容锁；即使 API 最终要拒绝操作，也要先取得这些锁。数据库会中断某一事务，表现为失败/重试，而非必然数据泄漏。
- 修复：所有相关 handler 和入口统一锁顺序与临界区，补下载完成与用户改稿/选图竞争测试；本地 SQLite 全绿不能验证此项。

### A28 · P2 · 真实业务链路仍会注入旧“地图/路线”Demo 语义【隔离函数复现】

- `models.py:22/51–54` 缺少或空 CTA 时默认“打开星图地图，规划适合自己的路线”。
- `review.py:67` 缺少产品名时，固定补“使用{产品名}整理路线信息”；`workflow.py:34` 的图片提示仍强加城市视觉。
- 探针：产品=社区食堂、CTA=查看今日菜单，修复输出加入“使用社区食堂整理路线信息”；另一个 ContentFlow brief 空 CTA 被替换为星图地图文案。
- 这不只存在于 Mock 文案；`content_agent.py` 真实草稿的规则修复及 `workflow_service.py` 的 Brief 解析会经过上述逻辑。Mock 内地图示例则应继续明确标为测试素材，不能混为真实模型效果。
- 修复：无行业事实时保留缺失/请求补齐；确定性规则只校验与安全变换，不擅自发明产品能力；城市、行业、视觉与 CTA 来自用户 Brief 或明示模板。用软件、餐饮、教育、实体产品等回归验证。
