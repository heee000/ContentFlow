## 3. 第一优先级：会直接影响可交付性的缺口

### A53 / P1（本轮新增归并）：安全升级流程没有闭环

**证据：** `deploy/public-test/deploy.sh:54` 仅在 API/Worker 正运行时备份；`:68–70` 启动数据库、执行 Alembic，再更新服务，前面没有停止旧 API/Worker。`contentflow/bootstrap_admin.py:174` 无论生产还是开发都调用 `upgrade_database()`。

临时 shell 故障注入确认：

- 正常分支记录了 migration、startup、release promotion，但没有任何 stop。
- 模拟已有数据库、API/Worker 已停止：`backup=false / migrated=true / promoted=true`。备份是否需要，不能只依据应用是否运行。
- 注入“stop 失败”没有被触发，因为脚本根本没调用 stop，仍然晋级；这是没有停写门禁，不是发现 Docker stop 本身失效。
- 备份或迁移显式失败确实会停止、不会写成功标记，已有 fail-closed 行为应保留。
- 两项管理员 CLI 正式测试证实，无论库已迁移还是未迁移，都先触发隐式迁移，而不是只做运行准入检查。

**影响：** schema 与旧执行者可能混用；停机后再升级反而遗漏备份；创建/添加管理员具有未预期的 DDL 副作用。当前执行权令牌和 staging 契约尤其不应与旧 Worker 混跑。未证明真实服务器已因此丢数据。

**关闭条件：** 预检和取镜像→停写/排空旧 Worker→确认数据库就绪→为现有数据备份→专用迁移身份显式迁移→同版 API/Worker/Web 启动与验证。迁移失败保持明确维护态，不能自动恢复不兼容旧代码；管理员 CLI 只检查，不自动修库。部署晋级还需核对实际 API/Worker 的候选版本，不能只接受任意近期 Worker 心跳。补 Linux/Windows 夹具、旧库升级、失败回退及同版恢复演练。

### A12 / P1：费用与资源硬约束不足

`contentflow/providers.py:440–475` 没有输出 token 硬上限，响应整体读取；`knowledge_service.py:78` 起将全部分块一次传给 Embedding；`schemas.py:258` 等 Brief 数组缺少条目数与元素长度上限。存储配额、登录限流和有限改写轮数已经有，但不是工作区调用预算、排队上限、公平调度或 Provider 并发限制。

合法账号误操作、大文档或异常上游响应就可能造成费用/内存/队列压力；不需要先出现匿名攻击。应在调用前做输入和分批限制、响应字节/token 限制、每区预算预留/结算、并发/积压上限；结果未知的费用不能直接释放后盲重试。预算、超时、取消、供应商幂等是不同契约，不能互相替代。

### A47 / P1：多平台失败会丢已完成的可编辑稿

`workflow_service.py:192–210` 先将各平台结果保存在内存，全部结束后才创建内容。本轮实际 Worker 的调用顺序为 `plan → 微信 generate/review → 抖音 generate 故障`，最终 `run=failed / contents=0`。`result_json` 有 `ai_provenance`，不能说所有调用证据都丢了；问题是已完成稿件不能继续编辑使用。

应按平台/阶段持久检查点，保留 partial_success，并绑定输入/Prompt/模型身份；只续作确定未完成的阶段，不能自动重放结果未知请求。先证明“第二个平台坏了，第一篇还在”，再谈更复杂的 Agent 编排。

### A39 / P1：素材就绪状态不保证是真素材

实际 `asset.generate` Worker 接收 `b"not an image"` 和 `image/png` 后，得到 `job=succeeded / asset=ready / bytes=12 / stored=true`。`worker.py:882` 的 `_store_generation` 在写入后约 `:982` 标记 ready，没有统一实际解码校验。

人工上传/部分搜索处理已有校验，不能说全部入口都没有。应统一生成、轮询、下载、上传的接入规范：真实格式、可解码、尺寸/像素/时长/体积及必要安全处理通过后才能 ready。这里证明的是损坏文件可进入业务状态，不是已证明任意代码执行。

### A40 / P1：审核对象与最终发布字段不一致

禁用词“稳赚不赔”只放入 hashtags，规则返回 passed=true；放入正文的正对照返回 false。证据 `review.py:34`、`review_evidence.py:122`；后者重新审核也只传 title/body。

需要统一“实际发送/导出的内容载荷”：标题、正文、CTA、标签、脚本等适用字段和最终渠道渲染均受版本绑定审核。人工例外应明确记录，不能让系统把根本没检查过的字段标成已通过。人工审核门禁仍在，本轮没有实际公开发布违规内容。

### A41/A51/A52 / P1 验收门槛：已有实现不等于已交付

保留新 schema 检查、短事务/charged staging、执行令牌与素材版本复核。当前 59 项跳过覆盖真实服务专项；新 schema 的 PG 只读事务/漂移、行锁交错、MinIO/S3 PUT 成功回执丢失、kill、回收竞争、f0 同版升级恢复均需实际签收。不要为了恢复旧测试或提高吞吐撤掉保护。

新 schema 检查每次 readiness 和生产 Worker 领取前反射结构，需测量真实 PG 开销；`SET LOCAL statement_timeout` 是逐语句限制，不是整个健康请求的总时限。此处是待测性能风险，不是已确认生产故障。

## 5. 内容产品还欠缺的核心能力

1. **内容质量评测不是模型自评。** `content_agent.py:104` deep 改写主要依赖 passed/总分，高分下重要修改指令未必触发。需要跨行业真实 Brief 集、人工盲评、事实错误率、可直接使用率、人工修改量、单篇耗时/成本；以版本对照证明进步。本轮没有真实模型样本，不能声称质量已提高或给出真实质量分。
2. **召回来源不是事实证据。** `knowledge_service.py:156/180` 有工作区过滤，但没有 embedding model/索引代次隔离及低相关性拒绝；`workflow_service.py:232` 保存所有召回 ID，不等于逐主张得到支持。先做模型身份/重建契约、相关性评测、主张与来源版本绑定，再判断混合检索/重排是否值得引入。
3. **一次生成仍不能完整复现。** Brief/style 有快照，但 `workflow_service.py:87/93` 执行时再取 active Prompt/当前 Provider。接受时固定非秘密配置指纹、Prompt/规则/索引版本；排队后换配置应有明确策略，不往快照塞密钥。
4. **最终成品适配不足。** 公众号图文排版、正文插图与图文对应、平台渲染预览；抖音成片/授权/状态对账；小红书人工导出分别需要真实验收。某个平台适配器存在不等于三个平台能力相等。
5. **素材来源与许可仍需产品闭环。** 搜到图片、能下载并不等于授权合适；应保留来源、许可、署名及选用记录，并验收封面与正文一致性。模型输出不能自行证明版权或真实性。

## 7. 安全、运维和企业完整性：尚缺验证的风险

这些不都等于已确认漏洞，也不是个人私测前必须一次性建设所有企业功能。

- **秘密生命周期：** 曾在聊天中直接给过凭据，应在公开部署前轮换/撤销并核对历史日志、备份和访问范围。本轮未读取或更改它们，不能声称发生了第三方泄漏。
- **最小权限：** 应用和数据库初始化角色尚未拆开，私测部署文档也明确承认。迁移角色与运行身份分离，限制对象存储权限；应用 workspace 过滤已有，但还需当前版本跨角色/跨租户负向矩阵与独立安全复核。RLS 可作纵深，不替代应用校验。
- **出网与供应链：** 已有端点校验/部分跳转限制，仍需目标部署的网络出口限制和恶意/异常 Provider 响应测试；没有确认可利用 SSRF。当前依赖未做新的在线扫描，旧扫描不能视作此刻安全证明。
- **告警接收：** `deploy/observability/README.md:50` 明确没有内置 receiver。需故障→通知到人→处置→恢复演练；有图表和规则不等于有值守。
- **联合恢复：** 当前数据库/pgvector/对象/密钥与配置的异机恢复、RPO/RTO、恢复后不重复发布尚无本批证据。数据库 dump 或备份命令成功不证明整个产品可恢复。
- **容量与长期稳定：** 2 核 4G 低并发私测可行，但应测队列积压、API 延迟、swap/OOM、磁盘、断网和重启；不凭一次跑通承诺无人值守。
- **账户和数据生命周期：** 恢复/撤权、会话管理、按需 MFA/OIDC；知识删除/失效对索引与衍生内容的传播、导出/保留/备份过期；企业按需求补编辑审核发布职责分离与独立审计保留。
- **交付责任：** 明确支持的平台/模型矩阵、版本兼容、发布与回退责任、问题受理和验收标准。没有这些，不能仅凭容器和 README 宣称企业商业成品。

## 8. 推进顺序与阶段判断

| 阶段 | 目前判断 | 最低额外门槛 |
| --- | --- | --- |
| 开发者陪同私测 | 可继续使用已明确验证的版本 | 不把在制失败候选直接部署；人工审核、备份、逐任务核对 |
| 普通用户独立个人自用 | 尚不足 | 收尾 A41/A53/A54 与存储验收，A39/A40、预算、部分成果保存、重启恢复和清楚的人工处置 |
| 私人公网可访问 | 暂不放行 | 前项 + 访问控制、密钥轮换、运行最小权限、限额/通知/备份恢复；公网 URL 本身不是交付 |
| 邀请制公开测试 | 暂不放行 | 当前 PG/MinIO/安全负向与容量验收，费用和滥用门禁，隐私/删除及回滚支持；限制人数和额度 |
| 企业完整商业项目 | 仍有显著差距 | 内容质量与 SLO、客户权限/数据治理、独立安全评估、支持/值守/灾备及版本承诺 |

建议顺序：

1. **收尾当前候选，不再添加平台。** 修管理员隐式迁移与部署停写/备份/模型选择，修测试夹具，取得同版 PG/MinIO/迁移恢复证据。
2. **建立可信的最小成品。** A39/A40/A28 媒体与最终字段验证；A12 调用预算/输入输出边界；A47 部分成果与安全续作，A46/A09 模式与配置快照。
3. **提升数据与内容质量。** A35/RAG、A33 指标、A16 同步、A34 Brief 并发；建立真实内容盲评和平台成品验收。
4. **降低使用成本。** 按用户任务收敛导航、按需请求、服务端历史查询、项目深链接和可恢复草稿。
5. **完成运行闭环再扩大测试。** 重新确认真实调用范围/预算后受控验收；通知、异机恢复、容量与限量长时运行通过后，才考虑公网和商业化。

不以“完成度 80%”衡量：一个费用或恢复硬门槛没过就足以阻断公开服务。当前也不需要为企业感急着上微服务/Kubernetes。此次仅审计记录，以上建议未被冒记为已修复；所有验证进程已结束。
